## 25.1 共享什么、不共享什么——一张表

团队场景下，**哪些跟项目走（共享）、哪些个人私有**？记住这张表：

| 文件 / 目录 | 共享（进 git） | 个人（不进 git） |
|------------|-------------|---------------|
| 项目 `CLAUDE.md` | ✅ 进 | |
| `.claude/commands/`（项目级命令） | ✅ 进 | |
| `.claude/skills/`（项目级 Skills） | ✅ 进 | |
| `.claude/agents/`（项目级 Subagents） | ✅ 进 | |
| `.claude/settings.json`（项目共用 hooks） | ✅ 进 | |
| **`.claude/settings.local.json`（个人覆盖）** | | ✅ 不进 |
| **`~/.claude/CLAUDE.md`（全局个人偏好）** | | ✅ 不进 |
| **`~/.claude/commands/`（个人命令）** | | ✅ 不进 |
| **MCP 配置（含凭证）** | | ✅ 不进 |
| **任何包含 token / API key 的文件** | | ✅ 绝不进 |

### 典型 `.gitignore` 示例

在项目根目录的 `.gitignore` 里加：

```gitignore
# Claude Code 个人设置 / 密钥
.claude/settings.local.json
.claude/mcp_servers.json       # 通常含凭证，别误传
.claude/*.log                  # 本地审计 log 不进 git
```

### 为什么这样分

- **共享**的是**团队共同的"工作方式"**——每个成员拿来就能一致工作
- **个人**的是**你自己的偏好或敏感凭证**——别人不需要、也不该看到

## 25.2 团队 CLAUDE.md 的维护节奏

### 初版怎么起

**第一个人建**：按 Ch 14 的模板，先写一个**最小版本**（20-30 行）。提 PR。

### 修改走 PR

之后任何人想改 CLAUDE.md——**走正常 PR 流程**：

- 不直接 push
- 改动**附带为什么**（"因为 2 月 15 日生产事故，以后禁止直接改 migration 文件"）
- 至少 1 人 review 同意

### 定期整理

**每季度**或**版本节点**：

- 扫一遍——有没有过时条目？
- 有没有重复 / 冲突？
- 能不能合并 / 砍短？

### 防止膨胀的硬线

团队 CLAUDE.md 比个人项目**更容易膨胀**——每个人都想加自己关心的规则。

**对抗方法**：
- 硬性上限（团队商量定，比如 < 150 行）
- 达到上限后**新加一条必须删一条**
- 争议大的放到专门文档（`docs/testing.md` 等），CLAUDE.md 只放 pointer

## 25.3 三个团队场景容易踩的坑

### 坑 1：密钥进了 git

**典型场景**：某人装了 GitHub MCP，配置文件里有 token，手滑 `git add .` 加上，push 了。

**后果**：
- GitHub 会自动扫描，**发现 token 会通知你**（但已经晚了）
- 坏人可能用这 token 干坏事——删 repo、改代码、发 issue

**预防**：
- **`.gitignore` 第一时间配好**（见 25.1）
- 配凭证前先**检查文件是不是被 git 追踪**：`!git status` 看
- 发现泄露——**立刻 revoke + 从 git 历史清除**（用 `git filter-repo` 等工具；简单情况可以新建仓库 re-import 干净版本）

### 坑 2：每个人标准不一致

**典型场景**：小明觉得"vibe review 就够"，小红每次都细审——同一段 PR，两人给的反馈完全不同步。

**后果**：
- 评审结论不统一
- 团队质量波动

**预防**（参见 Ch 10 支线 B）：
- **团队审核约定**——哪些类型的改动必须 L3 / L4（写进项目 CLAUDE.md）
- **定期 calibration 会议**——大家一起评一个真实 PR，对比标准差异
- **新成员入职**——把团队 CLAUDE.md + 审核约定作为必读

### 坑 3：成员各自装的扩展互不知道

**典型场景**：小明配了一个 Skill 帮他写测试，小红不知道——自己重头摸一遍。

**后果**：
- 重复劳动
- Skill 质量参差不齐（每个人自己维护）

**预防**：
- **团队 skills 进项目级 `.claude/skills/`**——进 git 共享
- 专门一个 channel / 文档**登记**谁加了什么 Skill / Command
- 新加的扩展要 PR review——让其他人知道

## 25.4 和 git 工作流的配合

Claude Code 和 git 是**天然搭档**——一些最佳实践：

### 实践 1：重要改动前先 commit

让 Claude 做大改动前：

```
你：先帮我跑 !git commit -am "work in progress" 保存当前状态
Claude：（跑 commit）
你：好，现在开始重构 @xxx
```

**好处**：重构出错想回退——`git reset` 到刚才的 commit。**比 `/rewind` 更硬核可靠**。

### 实践 2：分支 + Claude 探索

不确定方向时：

```
你：先切到一个新分支 claude-exploration，在这里试改；不行再换方法
```

试完：
- 方案好 → merge 回主分支
- 不好 → 直接删分支，什么都没留下

**比在主分支直接改更安全**。

### 实践 3：让 Claude 看 git 状态

Claude 经常不知道你的改动上下文。**先让它看状态**：

```
你：!git status
    !git log -n 5 --oneline
    现在基于这些信息，帮我 ...
```

### 实践 4：commit message 由 Claude 生成

改完后：

```
你：看 !git diff，为这次改动写一个 commit message
    （按我们项目的 conventional commit 风格）
Claude：（生成 `feat: ...` 风格消息）
```

**省你敲字 + 更规范**。

### 实践 5：标记 AI 参与的 commit

有些团队约定——AI 生成或深度修改的 commit 加**特殊标记**：

```
feat: add user batch import [AI-assisted]
```

或在消息里加：

```
Co-authored-by: Claude <claude@anthropic.com>
```

好处：**review 时旁人知道要多留意**。

## 25.5 团队第一次用的"30 天接入路线"

给刚要引入 Claude Code 的团队一个推荐节奏：

### 第 1 周：小范围试点

- 选 1-2 个 "**AI 好感度高 + 项目不太敏感**" 的成员
- 他们各自按本书 Part 1-2 上手
- **不动项目 CLAUDE.md**，先各自体验

### 第 2 周：建项目 CLAUDE.md v0.1

- 试点成员讨论出初版 CLAUDE.md（20-30 行）
- 提 PR，全员 review
- **不建议一次性把团队所有规矩都塞进去**——先最硬的几条

### 第 3 周：建团队审核约定

- 讨论哪些目录 / 文件 必须 L3 / L4 审核
- 哪些绝不能让 AI 动
- 写进 CLAUDE.md 或单独文档

### 第 4 周：扩展 + 共享

- 试点成员把已经好用的 Custom Commands / Skills 放到 `.claude/commands/` `.claude/skills/`（项目级）
- 全员 pull 下来就能用
- 收集反馈、微调

### 30 天后的常态

- 所有成员都用上
- CLAUDE.md 每月维护一次
- 新 Skill / Command 走 PR
- 月度回顾："哪些用得好、哪些没人用、CLAUDE.md 要不要砍"

## 本章小结

- **共享 vs 私有**：项目级目录下的所有东西共享、个人设置 + 凭证不共享
- **`.gitignore`** 第一件事配好——`.claude/settings.local.json` / `.claude/mcp_servers.json`
- **CLAUDE.md 走 PR**，每季度整理，硬性上限防膨胀
- **三个典型坑**：密钥进 git / 标准不一致 / 扩展不共享——各有预防方法
- **git 和 Claude 搭档**：重改前 commit / 分支试 / 先看状态 / 让 Claude 写 commit message / 标记 AI 参与
- **30 天接入路线**：第 1 周试点、第 2 周初版 CLAUDE.md、第 3 周审核约定、第 4 周扩展共享

## 动手任务

### 任务 1：给你的项目配 `.gitignore`（5 分钟）

**步骤**：

1. 打开（或新建）项目根目录的 `.gitignore`
2. 加入 25.1 的推荐行
3. `git status` 检查是否还有敏感文件被追踪；有的话用 `git rm --cached <文件>` 移除（文件保留本地）

**成功标志**：`git status` 里看不到任何含凭证或个人配置的文件。

### 任务 2：扫一下你现在的 git 历史（10 分钟）

**步骤**：

1. 在项目根跑：`!git log --all --full-history -- .claude/ 2>/dev/null | head -50`
2. 看有没有历史 commit 涉及敏感配置
3. 如果有 → **警觉**：去对应服务 revoke 所有 token，重建

**成功标志**：确认你的 git 历史里没有未处理的敏感泄露。

### 任务 3：写一份团队 30 天接入计划（15 分钟，如你要给团队引入）

**步骤**：照 25.5 的路线图，**具体到人、具体到日期**写出你团队的计划：

```markdown

## 第 1 周（4/22-4/28）试点
- 试点成员：张三、李四
- 他们各自读本书 Part 1-2

## 第 2 周（4/29-5/5）CLAUDE.md v0.1
- 5/2 前出初版 PR（张三负责起草）
- 全员 5/4 前 review + 合并

...
```

**成功标志**：你有了一份**能给老板看的**接入路线，不是空喊"我们要用 AI"。

## 如果你卡住了

**症状 A：同事不愿意用，觉得 AI 靠不住**
- 原因：合理——AI 有出错案例、别人可能听说过。
- 解决：**低风险任务起步**——让他们先用在"写周报草稿"这种最安全的任务，建立信任后再扩大。**不要强推**。

**症状 B：团队 CLAUDE.md 改动总是引起争吵**
- 原因：规则背后的价值观分歧。
- 解决：争议大的条目**先不进**——放到专门文档（`docs/style.md`）讨论，达成共识再移回 CLAUDE.md。

**症状 C：密钥已经 push 了怎么办**
- 原因：手滑或 `.gitignore` 晚了。
- 解决：**两步走**——① 立刻 revoke 泄露的 token / key；② 从 git 历史清除（用 `git filter-repo` 或 BFG Repo-Cleaner；力量不够就**新建一个干净仓库**重新 push）。**历史不清干净，泄露的凭证永远在**。

## 🌿 支线 25.A：Claude Code 和 CI/CD 的边界

> **这段讲什么**：有人问"能不能把 Claude 接到 GitHub Action 里自动审 PR"——能，但有边界。
> **什么时候回头读**：你的团队想把 AI 深度集成进自动化流水线时。

### 能做什么

- **PR 自动审核**：每次开 PR 触发一次 Claude 审查，结果评论到 PR
- **自动生成 CHANGELOG**：每次打 tag 让 Claude 生成发版说明
- **自动回复 issue**：常见问题 Claude 先答，人工 review

**具体怎么做**：用 Anthropic API + GitHub Action，或用 Claude Code 的非交互模式（`claude -p "..."`）。

### 不该做什么

- **Claude 自动 merge PR**：永远要人审——merge 是不可逆的
- **Claude 直接部署**：部署事故成本高，**人工批准 > 自动**
- **Claude 改生产配置**：永远不要给自动化流程改生产权限

### 一个踏实的入口

从**低风险 + 易观察**的开始：

- Claude 自动给 PR 打 summary 评论（只说看到了什么，不给评判）
- 观察几周，调整 prompt
- 质量稳定后再加审查评判
- **永远不自动化不可逆的事**

### 和本书定位的关系

本书是**零基础入门**——CI/CD 集成是**进阶话题**。先把交互式的 Claude Code 用熟、团队协作建好，再考虑 CI。
