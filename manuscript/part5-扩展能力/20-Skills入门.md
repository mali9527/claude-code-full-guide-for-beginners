## 20.1 Skill 是什么

**Skill** = 一份**预先写好的、针对特定任务的操作手册**，以 Markdown 文件的形式存在，Claude 在**需要时**自动加载进上下文，用完丢弃。

### 一句话定义

> 🔑 **Skill = 按需加载的任务手册。**

### 和 CLAUDE.md 的关键区别（复习）

| | CLAUDE.md | Skill |
|---|-----------|------|
| 加载 | **每次启动加载** | **按需加载** |
| 内容 | 全局规则、硬约束 | 特定任务的手册 |
| 适合什么 | "这个项目永远这样" | "偶尔做 X 任务时这么做" |

### 一个简单例子

假设你每月做一次"项目月报"。流程是：
1. 汇总本月所有提交
2. 整理关键成就 3-5 条
3. 列待办
4. 按固定模板排版

这个流程你一个月做一次——**放 CLAUDE.md 太浪费（占 Ctx 却 99% 时间用不到）**。

改成一个 Skill `monthly-report`：
- 平时不占 Ctx
- 你说"做月报"或 Claude 识别到类似需求时，**它才加载进来**
- 加载之后 Claude 按手册步骤做

### Skills 能放什么

- **结构化的任务流程**：月报、代码审查、发版流程
- **有固定模板的工作**：邮件回复、会议纪要、周报
- **多步推理的任务**：从数据到报告的完整管线

### Skills 不适合放什么

- **所有任务都适用的通用规则** → 放 CLAUDE.md
- **一次性任务** → 直接在 prompt 里讲就行
- **太复杂、步骤上百** → 拆成多个 Skill

## 20.2 Skills 存在哪里

两种位置（和 CLAUDE.md 类似）：

### 全局 Skills（只有你能用）

```
~/.claude/skills/<skill-name>/
```

### 项目 Skills（团队共享，进 git）

```
<项目根>/.claude/skills/<skill-name>/
```

### 一个 Skill 的最简文件结构

```
~/.claude/skills/monthly-report/
└── SKILL.md      # 就一个文件，其他都可选
```

**一个 Skill 的最小构成 = 一个 `SKILL.md`**——就是这么简单。

## 20.3 第一个 Skill：装一个现成的（15 分钟）

先**装别人写好的**——比从零写省事。

### 第一步：建目录

打开终端，跑：

```
mkdir -p ~/.claude/skills
```

（只建一次，之后所有 Skills 都放这下面）

### 第二步：新建 Skill 目录

我们做一个"会议纪要整理"Skill。

```
mkdir -p ~/.claude/skills/meeting-notes
```

### 第三步：建 SKILL.md

```
open -e ~/.claude/skills/meeting-notes/SKILL.md
```

（Windows 上用 `notepad %USERPROFILE%\.claude\skills\meeting-notes\SKILL.md`）

粘贴下面的内容：

```markdown
---
name: meeting-notes
description: 把凌乱的会议录音转写 / 笔记整理成结构化会议纪要
---

# 会议纪要整理

## 什么时候用

用户给你一段会议记录（语音转写、实时笔记、碎片发言），要把它变成结构化纪要。

## 输入

用户通常会给你一段凌乱的文字——可能是：
- 讯飞 / 飞书会议的录音转写
- 自己边听边记的笔记
- 多人轮流发言的原文

## 输出格式（固定）

```markdown
# 会议纪要：<会议主题>

- **时间**：<日期>
- **与会**：<名字列表>
- **主持**：<名字>

## 关键决定
1. ...
2. ...

## 讨论要点
- 要点 1：...
- 要点 2：...

## 行动项
| 事项 | 负责人 | 截止 |
|-----|-------|-----|
| ... | ... | ... |

## 悬而未决
- ...
```

## 原则

- 忠于原文——不要编造没提到的决定
- 不确定的细节（比如截止日期没说）就标 `<待确认>`
- 参会名单如果原文没列清楚，只写"与会多人"，不要乱填
- 按"决定 > 讨论 > 行动 > 悬而未决"排序

## 常见坑

- 原文里有闲聊 / 跑题——**剔除**
- 同一件事多人重复讲——**合并**
- 一个人说"我觉得应该 X"但没达成共识——放"讨论要点"，不放"关键决定"
```

保存。

### 第四步：试一试

在 Claude Code 里打开一个对话，找一段会议原始记录（随便从邮件、聊天记录拼一段假的也行），说：

```
你：用 meeting-notes 技能整理下面的会议记录：

（粘贴原始文字）
```

或者不指定技能，直接描述任务：

```
你：我有一段会议原始记录要整理成纪要，整理成结构化的样子。
（粘贴）
```

Claude 会自动判断需要用 `meeting-notes` Skill，加载进来，按手册做。

**成功标志**：输出严格按 SKILL.md 里的模板格式。

## 20.4 自己写一个 Skill（15 分钟）

写 Skill 没什么神秘的——**就是一份 markdown 说明书**。

### 步骤

1. **选一个你反复做的任务**（周报、邮件回复、代码审查、截图重命名...）
2. 想清楚这个任务的"标准流程"—— 输入是什么、输出什么样、有哪些规矩
3. 新建 `~/.claude/skills/<名字>/SKILL.md`
4. 按下面结构写

### 推荐结构

```markdown
---
name: <skill-name>   # 英文、连字符连接，Claude 引用时用
description: <一句话说它干什么>   # 这句是 Claude 判断"要不要用这个技能"的依据
---

# <标题，人类可读>

## 什么时候用
（什么场景触发这个 Skill —— 越具体越好，Claude 靠这个决定加载不加载）

## 输入
（用户会给你什么形式的原料）

## 输出格式
（你期望的最终产出是什么样——给模板）

## 原则
（不能违反的铁律）

## 常见坑
（历史上出过哪些错、怎么避免）
```

### 一个实例：周报生成

```markdown
---
name: weekly-report
description: 把本周流水账整理成老板喜欢的精简周报
---

# 周报生成

## 什么时候用
用户说"整理周报"、"写周报"、或丢给你一堆本周做的事让你汇总。

## 输入
- 一堆碎事项（多半按时间顺序）
- 有些是已完成、有些在做

## 输出格式

```markdown
# <姓名> 周报（<日期范围>）

## 本周亮点（1-3 条）
- ...

## 已完成
- 事项 1 — 一句话结果
- ...

## 进行中
- ...（标进度百分比）

## 下周计划
- ...

## 需要协助
- ...（没有就写"无"）
```

## 原则
- **亮点**永远是"有显著成果的事"，不是"我很努力做了 XX"
- 单项不超过 30 字，老板扫读友好
- "已完成"要有**结果**（"客户接入 3 家"），不能只写"做了对接"
- 不编造没做的事

## 常见坑
- 把所有做过的事都写成"亮点"—— 一条都不突出
- 用日期串起来的流水账 —— 按"已完成 / 进行中"分类更清晰
```

写完保存，跑一次看看效果。

### Claude 怎么知道什么时候用这个 Skill

两条路径：

1. **用户明说**："用 weekly-report Skill"
2. **Claude 自己判断**：看 `description` 字段 + `## 什么时候用` 描述，觉得匹配就加载

**关键**：`description` 要写准——这是 Claude 做决定的主要依据。

## 20.5 Skill vs CLAUDE.md 的选择心法

遇到一条"我想让 Claude 记住的流程"，按这张表判断：

| 情境 | 放 CLAUDE.md | 写 Skill |
|-----|------------|--------|
| 每次对话都相关 | ✅ | |
| 一个月才用一次 | | ✅ |
| 简短硬规则（1-2 行） | ✅ | |
| 结构化流程（多步骤、带模板） | | ✅ |
| 所有项目都适用 | ✅（全局 CLAUDE.md） | ✅（全局 Skills） |
| 步骤可能超过 50 行 | ❌（太大） | ✅ |

**核心判断**：**频率高 + 短 → CLAUDE.md；频率低 + 长 → Skill**。

## 本章小结

- Skill = 按需加载的任务手册，一份 markdown 文件
- 放在 `~/.claude/skills/<名>/SKILL.md`（全局）或 `.claude/skills/<名>/SKILL.md`（项目）
- 核心字段：`name` + `description` +「什么时候用 / 输入 / 输出 / 原则 / 常见坑」
- **频率高 + 短 → CLAUDE.md**；**频率低 + 结构化 → Skill**
- description 字段是 Claude 判断"要不要用"的主要依据——写准它

## 如果你卡住了

**症状 A：Claude 没自动识别 Skill，每次都要我明说**
- 原因：description 太模糊，Claude 判断不出匹配。
- 解决：description 要**说人话 + 关键词**——"把会议记录整理成纪要"比"会议相关的工具"好用。

**症状 B：SKILL.md 里写的东西 Claude 没执行到位**
- 原因：规矩写得太软（"尽量"、"建议"），Claude 理解有弹性。
- 解决：改成**明确指令**——"必须按这个模板"、"不得编造未提到的决定"。

**症状 C：不知道 Skill 有没有真的被加载**
- 原因：Claude Code 某些版本不显式告诉你。
- 解决：**看产出格式**——如果输出严格符合 SKILL.md 里定义的结构，说明加载了；完全不像就是没加载。

## 🌿 支线 20.A：Skill 的进阶结构

> **这段讲什么**：SKILL.md 之外还能放什么。
> **什么时候回头读**：你写了 3-5 个 Skill 后想把某个做大时。

### 多文件 Skill

复杂 Skill 可以有多个文件：

```
~/.claude/skills/code-review/
├── SKILL.md              # 入口 / 总览
├── checklist.md          # 审查清单
├── common-bugs.md        # 常见 bug 库
└── examples/             # 示例
    └── good-review.md
```

SKILL.md 里**引用其他文件**：

```markdown
## 审查流程

详细清单见 [checklist.md](./checklist.md)。
常见 bug 参考见 [common-bugs.md](./common-bugs.md)。
```

Claude 加载 SKILL.md 时会注意这些指针，需要时去读相关子文件。

### 给 Skill 加元数据

frontmatter 里可以加更多字段：

```markdown
---
name: code-review
description: 代码审查助手
version: 0.3
author: "我"
tags: [review, quality]
---
```

这些元数据**Claude 也能看到**，对它判断"这个 Skill 是不是最新版"有帮助。

### Skill 里调用其他工具

SKILL.md 里可以明确**指导 Claude 调用特定工具**：

```markdown
## 步骤
1. 用 `!git diff main` 获取变更
2. 用 @ 引用被修改的所有文件
3. ...
```

Claude 会照着做——相当于把操作流程固定住。

## 🌿 支线 20.B：Skill 共享 / 社区

> **这段讲什么**：你的 Skill 可以分享给团队 / 公开。
> **什么时候回头读**：你写了好的 Skill 想让别人用时。

### 团队共享

把 Skill 放**项目级**目录：`<项目>/.claude/skills/<名>/`

**进 git**，所有人 pull 下来就生效。

### 公开分享

- 发到 GitHub 单独仓库
- 别人 clone / 下载，放进自己的 `~/.claude/skills/` 即可

### 正在兴起的 Skill 社区

Anthropic 有官方 skill 目录、社区也在建立第三方集。搜 "claude-code skills" 或 "awesome claude skills"，找到合适的 fork 一份到本地用。

### 共享时的注意

- **不要在 Skill 里硬编码你的路径**（`/Users/yourname/...`）——用相对路径或占位符
- **不要在 Skill 里放密钥或个人信息**
- 写清楚 Skill 需要的**前提条件**（依赖哪些工具、哪些 CLAUDE.md 配置）
