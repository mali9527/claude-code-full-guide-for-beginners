<a id="121-比喻先行一个熬夜的人"></a>
## 12.1 比喻先行：一個熬夜的人

想象你身邊有一個很聰明的實習生，叫 Claude。他**腦容量有限**（就像人的短期記憶），當前能處理的材料有容量限制；這個比喻幫助理解“當前工作材料”，不能用一本小冊子的大小推算模型容量。

<!-- diagram: FIG-014 -->
![上下文像當前工作桌](../../../assets/illustrations/FIG-014/revisions/r02/zh-CN.png)

*圖：當前任務只攤開相關材料；整理會話不等於刪除磁碟檔案。*
<!-- /diagram: FIG-014 -->

一天開始時（對話剛開啟），他頭腦清晰，讀什麼都記得。

你不停和他對話、讓他讀檔案、讓他跑命令——這些內容一條一條**堆進他腦子裡**。小冊子越寫越滿。

材料過多、目標混雜或關鍵條件沒被保留時，可能出現：
- **想不清楚**：前面講過的細節想不起來
- **答非所問**：問 A 回答 B，因為"B"剛好在記憶裡更靠前
- **重複犯錯**：你前面糾正過的事，他又犯一遍
- **任務漂移**：原本讓他做 X，結果他做著做著變成做 Y

這些表現可能與上下文冗長、壓縮丟失細節有關，也可能是需求模糊、工具報錯或資料本身不完整。不要一見它出錯，就認定“視窗滿了”。先查實際佔用和出錯原因。

學會管理這個容量，你就解鎖了 Claude Code 的大半。

<a id="122-用技术名词说上下文窗口context-window"></a>
## 12.2 用技術名詞說：上下文視窗（context window）

上面那本小冊子，技術上叫**上下文視窗**。所有大模型都有這個限制，Claude 也不例外。

<a id="窗口里装了什么"></a>
### 視窗裡裝了什麼

- 你說的每一句話
- Claude 的每一句回覆
- 已經載入的檔案內容或片段（是否截斷、分頁或只讀取部分，取決於工具）
- 命令返回給模型的輸出（可能被截斷或儲存成檔案，但長輸出仍會增加負擔）
- CLAUDE.md 的內容（每次啟動都載入）
- Claude 自己的"系統提示"（Anthropic 給它的內部指令）
- 工具描述（能用哪些工具）


<a id="这个窗口多大"></a>
### 這個視窗多大

`token` 是模型處理資訊的計量單位，不等於固定數量的漢字。模型版本、語言和檔案內容都會影響換算，不必背“一個 token 等於幾個字”。

本版重點講的 **Fable 5.1 和 Opus 5.5** 在官方直接接入路徑支援 1M，也就是一百萬 token 上下文。但模型上限、當前接入能用的視窗，以及一次任務真正剩餘的空間，是三個問題。系統指令、工具、記憶、已聊過的內容和輸出預算都需要佔位置；閘道器或環境設定也可能改變實際視窗。[模型與上下文說明](https://code.claude.com/docs/en/model-config#extended-context)

可以把它想成一張更大的工作桌：桌面變大，能同時攤開更多資料，但雜物不會因此自動變得有用。只讀需要的材料、保留清楚的任務目標，仍比把整個硬碟交給它更有效。

<a id="123-看懂上下文先用-context再看状态栏"></a>
## 12.3 看懂上下文：先用 /context，再看狀態列

在 Claude Code 裡輸入：

```
/context
```

看看哪些內容佔了空間：對話、檔案、工具定義、記憶等。你不必理解每個內部名詞，先分辨“是不是剛讀了很大的檔案”“是不是日誌重複輸出很多”就有幫助。

有些介面或自定義狀態列會顯示 Ctx 百分比，有些沒有。**看不到固定的 Ctx 欄不代表安裝失敗**，也不要把 `/status` 當作上下文詳細報表。

<a id="不用百分比判断智商"></a>
### 不用百分比判斷“智商”

舊版把 50%、75%、90% 寫成固定警戒線，這容易誤導：沒有一條適用於所有任務和模型的“超過 75% 就明顯糊塗”的規則。

更實用的是看三個訊號：

| 你看到的情況 | 接下來做什麼 |
|---|---|
| 檔案或日誌佔了很多空間，但任務仍清楚 | 減少無關輸出，必要時壓縮 |
| 它反覆忘掉已確認的條件 | 重述關鍵條件，檢查是否需要整理或換會話 |
| 準備開始完全不同的一件事 | 儲存當前成果，再開始新會話 |

Claude Code 會在接近視窗限制時自動整理內容。你仍需檢查重要細節是否保留，別把“自動壓縮”理解成“永遠不會忘記”。[上下文的工作方式](https://code.claude.com/docs/en/how-claude-code-works#the-context-window)

<a id="不同任务消耗速度不同"></a>
### 不同任務消耗速度不同

- **純對話**：通常比大量工具輸出增長慢，但長回覆和多輪推理也會增加佔用
- **大量讀檔案** (`@` 多個大檔案)：**消耗極快**，`@` 一個幾萬字的 PDF 會明顯增加佔用，實際情況用 /context 檢視
- **跑命令輸出很長** (`git log -n 200`、`npm install` 的日誌)：同樣快速吃容量
- **上下文裡存在一個長 diff**：持續佔位

<a id="124-三种清理策略compactclear新会话"></a>
## 12.4 三種清理策略：/compact、/clear、新會話

當 Ctx 逼近警戒線，你有三個工具：

<a id="策略-acompact让-claude-自己整理思路"></a>
### 策略 A：`/compact`——讓 Claude 自己整理思路

**做什麼**：Claude 把當前對話**濃縮成關鍵要點**（去掉冗長的中間步驟和廢話），然後以摘要繼續當前工作；儲存的歷史記錄另當別論。

**效果**：Ctx 大幅下降（降幅取決於對話內容），**但保留核心共識和決策**。

**什麼時候用**：
- 任務還在進行中，**你不想從頭開始講**
- 對話裡有你反覆糾正的設定、達成的共識——這些要保留

**怎麼用**：
```
你：/compact
（Claude 花几秒生成摘要，你会看到一段"已压缩对话"的提示）
你：继续我们刚才的活
```

**注意**：
- `/compact` 是**有失真壓縮**——細節會丟。如果某個具體變數名、具體數字後面還要用，**最好自己在壓縮前記下來**。
- 可以在長任務中多次壓縮，沒有“只救一次”的固定限制。若每次壓縮後又被同一份巨型輸出塞滿，應先縮小讀取範圍。

<a id="策略-bclear开始一段新对话"></a>
### 策略 B：`/clear`——開始一段新對話

**做什麼**：結束當前對話上下文，開始新對話。磁碟上的專案檔案不會跟著消失。

**效果**：不再沿用剛才的工作上下文；系統指令、適用的專案說明和記憶仍可能載入，因此不是絕對 0。

**什麼時候用**：
- **任務已經做完**，開始下一個任務
- 對話已經嚴重跑偏，整理也救不回來
- 做的事和前面完全沒關係

**怎麼用**：
```
你：/clear
（Claude 重置，下一条消息开始就是全新对话）
```

**注意**：舊會話通常仍在記錄裡，可以用 `/resume` 查詢；`/clear` 不是刪除記錄或撤銷已上傳資料。為了順利接力，把重要結論寫入任務筆記，長期規則才放進 CLAUDE.md。

<a id="策略-c退出--新会话"></a>
### 策略 C：退出 + 新會話

**做什麼**：退出普通前臺會話（輸入 `/exit`，先檢查後臺任務），重新 `claude` 啟動。

**效果**：重啟客戶端。它不會自動刪除磁碟檔案、撤銷外部操作或清空賬號裡的資料。

**什麼時候用**：
- 換了一個**完全不同的專案**（跨 workspace）
- Claude 出現詭異行為，`/clear` 也救不回來
- 一天結束，收工

<a id="新开还是继续先分清"></a>
### 新開還是繼續，先分清

| 情況 | 用哪個 |
|------|-------|
| 任務正幹著，只是嫌 Ctx 高 | `/compact` |
| 任務告一段落，開始做下一件 | `/clear` |
| 換專案 / 客戶端卡住了 | 儲存進度，退出後進入正確目錄再啟動 |
| 昨天的任務還沒做完 | `claude --continue`，或 `claude --resume` 選擇舊會話 |

<a id="125-预防比清理更重要省-ctx-的-5-个习惯"></a>
## 12.5 預防比清理更重要：省 Ctx 的 5 個習慣

清理是"病了再治"。**預防**才能讓你更久保持清爽狀態。

<a id="习惯-1-引用时用具体路径不--整个文件夹"></a>
### 習慣 1：@ 引用時用具體路徑，不 `@` 整個資料夾

`@目录/` 提供檔案列表，不會自動加入全部正文；但要求“讀完裡面所有檔案”仍可能導致大量讀取。先指定任務相關的檔案，例如 `@src/components/Button.tsx`，再按需要補材料。

<a id="习惯-2先查目录和关键词再读相关段落"></a>
### 習慣 2：先查目錄和關鍵詞，再讀相關段落

對於可能很長的檔案：

```
你：先看长文档的标题和目录，找出与“退款条件”有关的部分。
Claude：（教学示意：列出有关小节）
你：只读这些小节，给出结论并标注原文位置。
```

如果先把全文塞進上下文，再要求摘要，已經發生的全文讀取不會被撤回。省空間的關鍵是縮小讀取範圍。

<a id="习惯-3跑命令限制输出"></a>
### 習慣 3：跑命令限制輸出

- `git log -n 10`（不是 `git log`，不設限制就全輸出）
- `ls src/` （不是 `ls -R /` 遞迴列出整個目錄）
- `cat 短文件.txt`（不是 `cat 一个 10MB 的日志`）

<a id="习惯-4每个任务完成就-clear"></a>
### 習慣 4：每個任務完成就 `/clear`

養成習慣：完成一件任務 → `/clear` → 開始下一件。**不要一個會話跨三天做十件事**。

<a id="习惯-5定期检查-ctx-数字"></a>
### 習慣 5：定期檢查 Ctx 數字

每幾輪對話瞥一眼狀態列。在任務轉折點問自己“接下來還需要哪些材料”，再決定繼續、壓縮或另開會話。

---

<a id="本章小结"></a>
## 本章小結

- 上下文是當前工作參考的材料，容量與相關性都需要管理；出錯時也要檢查任務、工具和資料本身
- 用 `/context` 檢視佔用；百分比是容量參考，不是模型質量分數
- 三檔清理：**`/compact` 整理當前任務；`/clear` 開始新對話；`/resume` 繼續儲存過的會話**
- 清理策略不對 → 要麼還是糊塗（該清沒清）、要麼丟了重要共識（清過頭）
- **預防 > 清理**：精準 `@`、限制命令輸出、每個任務完成就 `/clear`

<a id="动手任务"></a>
## 動手任務

<a id="任务-1观察-ctx-变化10-分钟"></a>
### 任務 1：觀察 Ctx 變化（10 分鐘）

**步驟**：

1. 啟動 Claude Code，用 `/context` 記下當前佔用，不預設起始百分比
2. `@` 引用一個你手頭的 Markdown 或 txt 檔案（選一份不敏感的小樣即可）→ 記下新的 Ctx
3. 請它列出練習目錄裡的檔案 → 再用 `/context` 檢視
4. 來回聊 5-10 輪普通對話 → 記下 Ctx
5. 執行 `/compact` → 記下 Ctx
6. 執行 `/clear` → 記下 Ctx

**成功標誌**：你現在直觀感受到"什麼操作消耗多、什麼消耗少"。

<a id="任务-2实战一次长任务--主动压缩15-分钟"></a>
### 任務 2：實戰一次"長任務 + 主動壓縮"（15 分鐘）

**步驟**：

1. 找一個你真實想做的稍長任務（讀 3-4 個檔案 + 寫一份報告）
2. 做完初步閱讀後，用 `/context` 看當前佔用
3. **主動執行** `/compact`，觀察 Claude 生成的摘要
4. 繼續做完剩下的部分
5. 結束後 `/clear`

**成功標誌**：你體驗了"任務中段主動整理"的節奏，能在繼續前核對關鍵結論是否保留。

<a id="任务-3建立你自己的-ctx-纪律5-分钟"></a>
### 任務 3：建立你自己的 Ctx 紀律（5 分鐘）

在你的**個人 Claude Code 使用筆記**（沒有就建一個 `~/Desktop/ccguide-练习/我的使用笔记.md`）裡寫下：

```markdown
# 我的 Ctx 纪律

- [ ] 每次启动后先看一眼状态栏
- [ ] 做大于 3 个文件的任务前，估计是否要 /compact
- [ ] 任务转折点查看 /context
- [ ] 压缩前把关键结论保存到任务笔记
- [ ] 每完成一个独立任务就 /clear
```

**成功標誌**：你有了一份能貼在工作流裡的個人約定。

<a id="如果你卡住了"></a>
## 如果你卡住了

**症狀 A：狀態列找不到 Ctx 數字**
- 原因：當前介面未配置相應狀態列，或顯示方式不同。
- 解決：執行 `/context`，不必為了一條狀態列先修改配置。

**症狀 B：/compact 後它忘了關鍵事情**
- 原因：壓縮是有損的，關鍵細節可能沒保留。
- 解決：**壓縮前自己記下"絕不能丟的 3 件事"**（比如具體的路徑、數字、約定），壓縮後再把這 3 條貼回去告訴它。

**症狀 C：對話沒多久 Ctx 就到 70% 了**
- 原因：你 @ 了大檔案或跑了長輸出命令。
- 解決：**別讓 Claude 讀整個大檔案**。改成：讓它先看目錄，你再 @ 具體哪一部分；命令加 `-n 20` 之類限量引數。

<a id="-支线-12atoken-是什么再深一层"></a>
## 🌿 支線 12.A：Token 是什麼——再深一層

> **這段講什麼**：上文多次提到 token，這裡說清楚 token 到底是什麼、為什麼不是"字元數"。
> **什麼時候回頭讀**：好奇為什麼一個漢字不等於一個字元、或想估算自己檔案要多少 token 時。

<a id="什么是-token"></a>
### 什麼是 token

Token 是模型處理文字的**最小單位**，但它不等於字元，也不等於單詞。


同一個詞可以被拆成幾段，常見組合也可能成為一個單元。你只需先記住：**字元數、檔案大小和 token 數是不同的量**。實際使用中不要根據某個舊模型的中文換算比例，給新模型做嚴格預算。

<a id="实用估算"></a>
### 實用估算

同樣一份中文材料，換一個分詞器，token 數也可能不同；圖片、表格和程式碼又有自己的表示方式。因此別用“這份文件只有幾頁”來推斷呼叫成本。

初學時用 `/context` 看實際佔用即可。準備處理很多文件時，先挑一份小樣，觀察載入與輸出，再決定分幾批完成。確有精確計數需求的開發者，可使用官方 [Token counting 介面](https://platform.claude.com/docs/en/build-with-claude/token-counting)。

<a id="为什么在意-token"></a>
### 為什麼在意 token

- **Ctx% 用的就是 token 比例**
- **API 用量按相應 token 費率計算**；訂閱額度與額外用量分開看（第 15 章）
- **`/compact` 的本質**：把原始幾萬 token 的對話**壓縮成幾千 token 的摘要**

<a id="怎么查一段文字多少-token"></a>
### 怎麼查一段文字多少 token

- 當前會話用 `/context` 看佔用。
- 精確計數需要使用所選模型對應的工具；普通日常任務不必手工逐字計算。

<a id="-支线-12b1m-窗口应该怎样用"></a>
## 🌿 支線 12.B：1M 視窗應該怎樣用

> **這段講什麼**：模型支援大視窗之後，日常工作怎樣安排。
> **什麼時候回頭讀**：準備比較很多份材料，或處理持續較久的任務時。

<a id="先看资料之间有没有关系"></a>
### 先看資料之間有沒有關係

如果你想比較十份同類報告，把它們放在同一任務裡可能很有幫助：模型需要對照相同口徑、發現差異。反過來，把購物清單、小說草稿和報錯日誌放在一個會話裡，即使視窗放得下，也不會自動改善結果。

先告訴 Claude 比較什麼，再讓它逐步讀取。重要結論要能指回檔案和位置，便於你抽查，而不是以“已經讀了很多”作為完成標準。

<a id="大窗口不等于固定高价套餐"></a>
### 大視窗不等於固定高價套餐

“1M”描述容量，不直接回答這次花多少錢。真實成本取決於模型、輸入輸出數量、快取、賬號計劃和使用額度。不要沿用舊稿“選 1M 一定加價五到十倍”的說法。具體賬單在第 15 章看。

同時，大容量不是準確率保證。一次帶入更多文字，可能增加處理時間和核對負擔。你的目標是完成任務，不是把視窗用滿。

<a id="发现实际空间与模型宣传不一致"></a>
### 發現實際空間與模型宣傳不一致

先用 `/model` 確認當前模型，再用 `/context` 看會話情況。公司閘道器、自定義模型名或限制上下文的環境變數，可能改變客戶端採用的視窗；不要隨意給第三方模型名追加 `[1m]` 來“解鎖”。

新版還可以透過 `/autocompact` 檢視和調整自動壓縮視窗。初學先保留預設值；如果由組織管理或環境變數覆蓋，命令會受到相應限制。需要修改時，先讀[自動壓縮視窗說明](https://code.claude.com/docs/en/model-config#context-window-and-auto-compaction)，並記錄為什麼要改。

<a id="-支线-12ccompact-的工作原理"></a>
## 🌿 支線 12.C：/compact 的工作原理

> **這段講什麼**：`/compact` 到底是怎麼壓縮的？
> **什麼時候回頭讀**：你想搞清楚它保留什麼、丟什麼時。

<a id="压缩过程"></a>
### 壓縮過程

1. Claude 讀完整個當前對話
2. 生成一個**結構化摘要**，大致包括：
   - 總目標是什麼
   - 已完成的關鍵步驟
   - 重要的決策和約定
   - 還未完成的子任務
   - 關鍵檔案路徑和符號名
3. 當前工作上下文使用摘要；儲存的會話記錄與當前載入內容是兩回事
4. 上下文從"幾萬 token 長對話" → "幾千 token 摘要" → Ctx% 大幅下降

<a id="保留什么丢什么"></a>
### 保留什麼、丟什麼

✅ 通常**保留**：
- 最終決策和約定
- 你反覆強調的要求
- 還沒做完的事

❌ 通常**會丟**：
- 你糾正過程中的曲折細節
- 早期被否決的方案
- 冗長的命令輸出
- 程式碼的完整內容（會變成"已讀過 XX 檔案"的記號）

<a id="怎么让压缩更聪明"></a>
### 怎麼讓壓縮更聰明

壓縮前對 Claude 說：

```
你：在 /compact 之前，请先列出你打算保留的 5 个关键点，
    让我确认有没有遗漏。
Claude：好的，我打算保留：
    1. ...
    2. ...
    ...
你：（检查）第 2 点里别漏了 X 的决定。
（核对后，单独发送下一行）
/compact 保留 X 的决定和当前待办
```

這樣壓縮質量高很多。
