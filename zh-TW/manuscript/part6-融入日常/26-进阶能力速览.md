<a id="261-新模型先试熟悉任务不必立刻改造全部流程"></a>
## 26.1 新模型先試熟悉任務，不必立刻改造全部流程

模型換代和 Claude Code 功能更新是兩條線。安裝了較新的 Claude Code，不代表賬戶裡每個模型都已經開放；選到了新模型，也不代表所有外部連線、自動化方式都支援同樣的配置。Fable 5.1、Opus 5.5 的選擇與接入條件，先看第 15 章和附錄 J，再以你的模型選單與官方當期說明核對。

比較時找一項你已經會驗收的任務：同一篇文件找錯、同一段程式補測試、同一組材料寫摘要。給各模型相同材料和目標，記錄完成程度、遺漏、你需要返工的地方，以及耗時和用量。不要只比“回答有沒有更長”，也不要把一次成功當成所有任務都更優。

需要更深入推理時，先確認任務說明和輸入已經齊全，再考慮調整模型或思考強度。沒提供關鍵檔案卻要求最高強度，可能只是讓模型更認真地猜測。反過來，簡單整理任務也不必為了使用最新名字而增加成本。穩定的流程保留不動，把模型選擇作為其中一個可比較的因素，升級時會輕鬆得多。

<a id="262-想换个界面还是想换台机器执行"></a>
## 26.2 想換個介面，還是想換臺機器執行

**Desktop 是圖形介面**，適合在一個視窗裡看會話、檔案和修改差異；具體入門看[附錄 H](../%E9%99%84%E5%BD%95/H-%E6%A1%8C%E9%9D%A2%E5%BA%94%E7%94%A8%E5%AF%BC%E8%A7%88.md)。開啟桌面應用後也應看清當前會話的執行環境，不能把“在桌面視窗裡看到它”理解為“一定在本機執行”。

**Remote Control（遠端控制）**讓你從手機或瀏覽器繼續本地會話。實際讀寫仍發生在原來的電腦，相關程序需要繼續執行；手機是另一扇控制視窗，不是替電腦接手執行任務的機器。比如你離開書桌想看本地測試結果，可以從當前會話的 `/remote-control` 入口瞭解是否可用。登入方式、組織策略和接入服務會影響可用性。[遠端控制說明](https://code.claude.com/docs/en/remote-control)

**Cloud（雲端會話）**則在遠端環境執行。它需要取得對應倉庫和執行依賴，不會自動擁有你電腦上尚未儲存或尚未上傳的檔案。準備交給雲端前，先問“它拿到的是哪份資料”，再問“能執行多久”。只有把輸入交代清楚，換執行地點才有意義。[雲端工作說明](https://code.claude.com/docs/en/claude-code-on-the-web)

這三者都可以幫你接續工作，但改變的是不同層面。先確定要解決的是“看起來方便”“離開電腦仍能操作”，還是“本機不線上也要執行”，就不容易選錯入口。

<a id="263-三种定时方式依赖条件不同"></a>
## 26.3 三種定時方式，依賴條件不同

定時任務是讓系統在約定時間再次執行提示詞。選它之前，要先知道誰負責等到那個時間：當前會話、桌面應用，還是雲端服務。

| 方式 | 適合的需求 | 執行條件 |
|---|---|---|
| CLI 的 `/loop` | 當前工作期間，反覆檢查一個狀態 | 依賴本地會話與執行中的程序 |
| Desktop 本地計劃 | 定期處理這臺電腦上的檔案 | 電腦喚醒、桌面應用執行；無需原聊天視窗一直開著 |
| 雲端 Routines | 本機不線上時仍執行預先定義的任務 | 使用為任務配置的遠端資料與環境 |

例如你正在等一次構建完成，可以讓 `/loop` 定期檢查。它不是獨立的永久服務；恢復原會話時部分任務可按規則恢復，但這不等於程序退出期間仍有人執行。[會話內排程](https://code.claude.com/docs/en/scheduled-tasks)

如果是每天整理本地資料，檢視 Desktop 的本地計劃。電腦睡眠時不能按原定時間執行，喚醒後可能按當前規則補最近一次，所以提示詞最好寫清“整理上一個完整日期的材料”，不要只寫含義模糊的“今天”。[桌面計劃任務](https://code.claude.com/docs/en/desktop-scheduled-tasks)

希望不依賴本機時，可以瞭解 **Routines（預先儲存的雲端例行任務）**，入口包括 `/schedule`。它仍處於研究預覽，執行資料、聯結器和許可權必須事先配好；不要期待無人值守時還能像普通聊天一樣逐步問你每個操作是否同意。[雲端 Routines](https://code.claude.com/docs/en/routines)

本章只建立選擇依據，**不會因為讀到示例就建立任何定時任務**。真正配置時，先手動執行一遍，核對輸出位置、失敗處理、用量與關閉方法，再儲存日程。

<a id="264-任务更多时先拆责任再谈自动化"></a>
## 26.4 任務更多時，先拆責任，再談自動化

第 22 章的子智慧體適合有明確範圍的專項閱讀與審查。如果確實需要多條工作線並行，再研究團隊協作或更復雜的任務編排。先寫清誰負責哪個檔案、誰彙總結論、誰驗證最後結果，不要只是給同一個模糊目標配上多個“專家”稱號。

需要把 Claude Code 接入指令碼時，可以使用**非互動模式**：程式接收一次請求並輸出結果，而不一直顯示普通聊天介面。下面僅展示形態，不是要你馬上批次處理檔案：

```bash
claude -p "只阅读 README.md，用三句话说明这个练习项目做什么，不修改文件。"
```

開始前應明確當前目錄、認證方式和可用許可權；指令碼里還要處理失敗、超時、重複執行與輸出儲存，不能只寫一個迴圈就跑上百次。具體引數看[程式化使用文件](https://code.claude.com/docs/en/headless)。

**CI（持續整合）**指倉庫發生變更時自動執行檢查的流程。你可以讓 AI 生成審查意見、輔助寫測試，但仍需要真正執行專案檢查，不能把“AI 說沒問題”直接當作釋出條件。要在自有應用裡使用這些能力，再學習 [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)。SDK 是給程式呼叫的開發工具，不是零基礎讀完本書必須補上的課程。

<a id="265-选一条路线把结果留下来"></a>
## 26.5 選一條路線，把結果留下來

進階不一定意味著自動化。你可能只是需要更清楚地審閱差異、更可靠地恢復工作，或者把每天重複的話整理成一個技能。先回看最近三次任務，哪一步花了最多時間，再選對應能力。

| 你目前最想改善什麼 | 先做什麼 |
|---|---|
| 看修改更清楚、管理多個任務 | 用附錄 H 的練習試 Desktop |
| 離開電腦後看本地任務進展 | 瞭解 Remote Control 的條件 |
| 定期處理本地或倉庫材料 | 先區分本節的三種排程方式 |
| 主對話材料太多 | 試一個有邊界的子智慧體 |
| 同類輸出質量不穩定 | 固定例子、結果標準與失敗樣例，再改技能或提示詞 |
| 整合到自己的程式 | 瞭解非互動模式與 Agent SDK |

每次試驗留下三件東西：給它的材料、你期待的結果、實際觀察到了什麼。排查問題時再增加具體日誌，不必為了“可觀測性”這個詞記錄所有私人輸入。日誌可以幫助查錯，但它不是任務真的成功的替代品，也可能含有檔案內容或賬戶資訊，分享前需要檢查。

本章沒有承諾某一種工具永久更便宜、更快，也沒有要求追完所有更新。你只需要能說清楚：這條路線解決哪個瓶頸，代價是什麼，失敗時怎樣回到原來可工作的方式。

<a id="本章小结"></a>
## 本章小結

- 模型升級、功能升級和賬戶可用性要分別核對。
- Desktop 是使用介面；Remote Control 保留本地執行；Cloud 使用遠端環境。
- `/loop`、桌面本地計劃和雲 Routines 的執行依賴不同。
- 編排和程式呼叫需要明確失敗處理、職責與驗收。
- 從一個真實瓶頸選一條路線，不必同時學習全部功能。

<a id="动手任务"></a>
## 動手任務

**任務 1，約 10 分鐘：**選擇一項真實工作，寫明它的材料在本地還是遠端、是否必須離線時執行、是否會修改外部內容。成功標誌是你能據此選中一種執行方式。

**任務 2，約 10 分鐘：**開啟該方式的官方說明，記錄適用條件與關閉方法，再設計一次只讀的小試驗。成功標誌是你知道怎樣證明它成功，而不僅是找到入口。

<a id="如果你卡住了"></a>
## 如果你卡住了

**選單裡沒有介紹的入口：**檢查執行環境、賬戶資格、組織設定和客戶端版本，不要直接認為安裝壞了。

**電腦休眠後任務沒按時執行：**先判斷你用的是本地計劃還是雲端任務；改變提示詞不能讓已關機的本地程序工作。

**感覺路線太多：**暫時不增加能力，繼續用前面章節完成實際任務。沒有遇到明確瓶頸，就沒有必須學習下一種工具的理由。

<a id="-支线-26a怎样读新功能发布消息"></a>
## 🌿 支線 26.A：怎樣讀新功能釋出訊息

這段講更新篩選；當一週出現很多新名詞時回來讀。

把訊息拆成三個問題：改變了什麼，適用於誰，有沒有改變你當前的工作方式。某個功能可以執行上百個並行任務，並不說明你寫一份週報也需要同樣規模；某個模型在基準測試裡領先，也不直接證明它更適合你的材料。

可以維護一張很短的觀察表：功能、官方連結、核驗日期、準備測試的任務、是否已經試過。只記錄你可能用到的專案。社群示範可以帶來靈感，但復現時要保留環境差異和失敗結果；沒有真實賬號、沒有對應作業系統，就寫“尚未驗證”，不要把一張宣傳截圖寫成自己已經跑通的步驟。

<a id="-支线-26b为自动化写明确的停止条件"></a>
## 🌿 支線 26.B：為自動化寫明確的停止條件

這段講長期執行的約束；當你準備啟用定時或無人值守流程時回來讀。

一次普通對話不滿意，你通常會立刻糾正。自動化會在你不在場時再次執行，所以需要提前說明遇到什麼狀態就停止：資料缺失時不要編寫報告、同一個失敗連續出現時停止重試、沒有新的變化時不重複生成同樣檔案。輸出也應能辨認本次用了什麼日期與資料，避免下一次誤把舊結果當成新結果。

這些約束必須配合實際執行機制。提醒模型“別花太多錢”不是計費上限；在文字中寫“只讀”也不等於服務端只給了讀取許可權。先把可訪問的目錄、倉庫、工具範圍和執行預算配置好，再用小試驗確認。停止後應能知道已做了哪些動作、哪些尚未完成，才能決定繼續、修改還是撤銷。
