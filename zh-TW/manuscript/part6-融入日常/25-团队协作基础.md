<a id="251-共享什么不共享什么一张表"></a>
## 25.1 共享什麼、不共享什麼——一張表

團隊場景下，**哪些跟專案走（共享）、哪些個人私有**？先看檔案的作用，再看內容。下面的“進 Git”都以經過稽核、不含憑據或個人材料為前提，不能因為放進專案目錄就直接公開。

<!-- diagram: FIG-028 -->
![共享桌與個人抽屜](../../../assets/illustrations/FIG-028/revisions/r01/zh-CN.png)

*圖：團隊共享工作約定，個人偏好與私密材料另行管理。*
<!-- /diagram: FIG-028 -->

| 檔案 / 目錄 | 共享（進 git） | 個人（不進 git） |
|------------|-------------|---------------|
| 專案 `CLAUDE.md` | ✅ 進 | |
| `.claude/commands/`（專案級命令） | ✅ 進 | |
| `.claude/skills/`（專案級 Skills） | ✅ 進 | |
| `.claude/agents/`（專案級 Subagents） | ✅ 進 | |
| `.claude/settings.json`（專案共用設定，例如 Hooks） | ✅ 稽核後進 | |
| **`.claude/settings.local.json`（個人覆蓋）** | | ✅ 不進 |
| **`~/.claude/CLAUDE.md`（全域性個人偏好）** | | ✅ 不進 |
| **`~/.claude/commands/`（個人命令）** | | ✅ 不進 |
| 專案 `.mcp.json`（已檢查不含憑據的共享定義） | ✅ 經稽核後進 | |
| 使用者或本地 MCP 憑據 | | ✅ 不進 |
| **任何包含 token / API key 的檔案** | | ✅ 絕不進 |

<a id="典型-gitignore-示例"></a>
### 典型 `.gitignore` 示例

在專案根目錄的 `.gitignore` 里加下面這些規則。**註釋要單獨一行**，不能放到檔案模式後面：

```gitignore
# Claude Code 的个人设置
.claude/settings.local.json

# 本地环境与凭据文件
.env
.env.*

# 本项目生成在此处的本地日志
.claude/*.log
```

這裡沒有把整個 `.claude/` 忽略掉，因為團隊的 Skills、Agents 和共同設定還需要共享。若使用不含真實憑據的 `.env.example` 模板，可以稽核內容後再新增對應的例外規則。其他位置的日誌或憑據，也應按實際路徑單獨處理。

還有一個容易誤會的地方：**`.gitignore` 隻影響尚未被跟蹤的檔案，不會讓已經提交過的檔案從 Git 中消失**。而 `git status` 主要顯示變動；已跟蹤且沒有變化的憑據檔案可能根本不出現在結果裡。[Git 忽略規則說明](https://git-scm.com/docs/gitignore)

下面是兩個不同檢查，在**專案根目錄的普通終端**分別執行：

```sh
git check-ignore --no-index -v -- .env .claude/settings.local.json
```

這條檢查這些路徑會匹配哪一條忽略規則。隨後執行：

```sh
git ls-files -- .env '.env.*' .claude/settings.local.json
```

第二條檢視這些路徑是否已在 Git 的跟蹤列表裡；有輸出就需要逐項檢查。兩條命令檢查的是指定路徑，不是給整個專案頒發“無金鑰證明”。[Git 跟蹤檔案查詢](https://git-scm.com/docs/git-ls-files)

<a id="为什么这样分"></a>
### 為什麼這樣分

- **共享**的是**團隊共同的工作方式**——便於成員用相同標準開始；實際可用性還取決於版本、依賴、個人授權與組織設定
- **個人**的是**你自己的偏好或敏感憑證**——別人不需要、也不該看到

<a id="252-团队-claudemd-的维护节奏"></a>
## 25.2 團隊 CLAUDE.md 的維護節奏

<a id="初版怎么起"></a>
### 初版怎麼起

**第一個人建**：按 Ch 14 的模板，先寫一個**最小版本**（20-30 行）。提 PR。

<a id="修改走-pr"></a>
### 修改走 PR

之後任何人想改 CLAUDE.md——**走正常 PR 流程**：

- 透過分支和 PR 修改，按團隊分支保護規則合併
- 改動**附帶為什麼**（"因為 2 月 15 日生產事故，以後禁止直接改 migration 檔案"）
- 至少 1 人 review 同意

<a id="定期整理"></a>
### 定期整理

**每季度**或**版本節點**：

- 掃一遍——有沒有過時條目？
- 有沒有重複 / 衝突？
- 能不能合併 / 砍短？

<a id="防止膨胀的硬线"></a>
### 防止膨脹的硬線

團隊 CLAUDE.md 比個人專案**更容易膨脹**——每個人都想加自己關心的規則。

**對抗方法**：
- 硬性上限（團隊商量定，比如 < 150 行）
- 達到上限後**新加一條必須刪一條**
- 爭議大的放到專門文件（`docs/testing.md` 等），CLAUDE.md 只保留必要說明與準確路徑

CLAUDE.md 用來向模型說明約定，不能代替許可權配置、分支保護或人工稽核要求。需要強制執行的邊界，應由相應系統落實。

<a id="253-三个团队场景容易踩的坑"></a>
## 25.3 三個團隊場景容易踩的坑

<a id="坑-1密钥进了-git"></a>
### 坑 1：金鑰進了 git

**典型場景**：某人裝了 GitHub MCP，配置檔案裡有 token，手滑 `git add .` 加上，push 了。

**後果**：拿到有效 token 的人可能以它的許可權訪問倉庫或其他服務。GitHub 的金鑰掃描可以發現部分憑據，但覆蓋範圍取決於金鑰型別、倉庫與配置，不能等待通知後再處理。

**預防與處理**：

- 提前配置 `.gitignore`，並用上一節的兩種檢查區分“規則匹配”與“已經跟蹤”。
- 每次提交前稽核暫存內容，尤其是新增配置檔案；不要依賴一次 `git add .` 自動分清共享與私有。
- 若金鑰已經進入共享歷史，**先到提供方撤銷或輪換這把金鑰**，再檢查其使用記錄，並讓維護者按倉庫情況處理歷史、快取、PR 與克隆。刪除當前檔案或換一個新倉庫，都不會清掉其他副本。

涉及共享倉庫的歷史改寫，要與維護者協調，不能獨自強推覆蓋團隊歷史。具體步驟以 [GitHub 敏感資料處理說明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)為準。

<a id="坑-2每个人标准不一致"></a>
### 坑 2：每個人標準不一致

**典型場景**：馬力覺得"vibe review 就夠"，小紅每次都細審——同一段 PR，兩人給的反饋完全不同步。

**後果**：
- 評審結論不統一
- 團隊質量波動

**預防**（參見 Ch 10 支線 B）：
- **團隊稽核約定**——哪些型別的改動必須 L3 / L4（寫進專案 CLAUDE.md）
- **定期 calibration 會議**——大家一起評一個真實 PR，對比標準差異
- **新成員入職**——把團隊 CLAUDE.md + 稽核約定作為必讀

<a id="坑-3成员各自装的扩展互不知道"></a>
### 坑 3：成員各自裝的擴充套件互不知道

**典型場景**：小明配了一個 Skill 幫他寫測試，小紅不知道——自己重頭摸一遍。

**後果**：
- 重複勞動
- Skill 質量參差不齊（每個人自己維護）

**預防**：
- **團隊 skills 進專案級 `.claude/skills/`**——進 git 共享
- 專門一個 channel / 文件**登記**誰加了什麼 Skill / Command
- 新加的擴充套件要 PR review——讓其他人知道

<a id="254-和-git-工作流的配合"></a>
## 25.4 和 git 工作流的配合

Claude Code 和 git 是**天然搭檔**——一些最佳實踐：

<a id="实践-1先审核再保存一个可恢复版本"></a>
### 實踐 1：先稽核，再儲存一個可恢復版本

想讓 Claude 重構幾個檔案，可以先這樣交代。下面是**教學示意**，實際檔名換成自己的：

```
先查看 git status 和本轮相关差异。
列出建议保存的文件，包括尚未被 Git 跟踪的新文件。
请先不要提交；我确认文件清单和暂存内容后，再创建一次本地提交。
```

如果自己操作，基本順序是：檢視狀態 → 選擇需要儲存的具體檔案 → 暫存 → 檢查暫存差異 → 本地提交。不要把“一次提交”理解為整個目錄都備份了；Git 只儲存實際進入該提交的內容。`git commit -am` 也不會自動納入尚未被跟蹤的新檔案。[Git 提交說明](https://git-scm.com/docs/git-commit)

儲存後記下提交號。需要恢復時，先比較當前差異，再選擇具體檔案或適合專案的恢復方式；`git reset` 的不同模式影響不同，不能當成一句不帶條件的通用撤銷。還不會 Git，就先複製一份練習資料，並按第 6 章的恢復說明操作。

<a id="实践-2用分支探索分清它与工作区"></a>
### 實踐 2：用分支探索，分清它與工作區

分支用來組織提交歷史。開始探索前先檢視狀態，把已有改動儲存或明確分開，再要求：

```
请确认当前分支和未提交改动。
在不丢失现有工作的前提下，新建 claude-exploration 分支，
只尝试我们刚讨论的方案；先不要合并或发布。
```

試完後檢視差異與驗證結果。方案可用，就按團隊 PR 流程合併；方案不合適，先確認哪些改動已提交、哪些還在工作區，以及哪些需要保留，再處理恢復。

**刪除分支不會自動撤銷工作區改動，也不會撤銷已產生的外部操作。** 在同一目錄切換分支時，部分未提交改動還可能隨之保留。需要並行隔離檔案時，可進一步學習獨立 worktree；它也不能隔離外部資料庫或服務的副作用。[Git 分支說明](https://git-scm.com/docs/git-branch)

<a id="实践-3让-claude-看到准确的-git-状态"></a>
### 實踐 3：讓 Claude 看到準確的 Git 狀態

可以直接用自然語言讓它檢視，也可以自己輸入 shell 模式命令。後者每次**單獨提交一條**：

```
!git status
```

檢查回應後，再提交：

```
!git log -n 5 --oneline
```

然後用普通訊息說明接下來的任務。不要在一段普通提示中間加 `!`，就以為每一行都會被當成 shell 命令。`!` 的許可權與費用行為見第 19 章。

<a id="实践-4让-claude-起草提交说明"></a>
### 實踐 4：讓 Claude 起草提交說明

檔案修改完成後，可以要求：

```
请查看这次准备提交的差异，为它起草一条提交说明。
先区分暂存、未暂存和未跟踪文件，只描述我已确认要提交的部分。
先不要提交或推送。沿用项目现有的提交说明格式。
```

稽核時，提交說明要能解釋**為什麼改、結果有什麼變化**。一句漂亮的說明不能證明程式碼或文件已經檢查過；驗證結果仍需單獨確認。

<a id="实践-5标记-ai-参与的-commit"></a>
### 實踐 5：標記 AI 參與的 commit

有些團隊約定——AI 生成或深度修改的 commit 加**特殊標記**：

```
feat: add user batch import [AI-assisted]
```

或在訊息里加：

```
Co-authored-by: Claude <claude@anthropic.com>
```

好處：**review 時旁人知道要多留意**。

<a id="255-团队第一次用的30-天接入路线"></a>
## 25.5 團隊第一次用的"30 天接入路線"

給剛要引入 Claude Code 的團隊一個推薦節奏：

<a id="第-1-周小范围试点"></a>
### 第 1 周：小範圍試點

- 選 1-2 個 "**AI 好感度高 + 專案不太敏感**" 的成員
- 他們各自按本書 Part 1-2 上手
- **不動專案 CLAUDE.md**，先各自體驗

<a id="第-2-周建项目-claudemd-v01"></a>
### 第 2 周：建專案 CLAUDE.md v0.1

- 試點成員討論出初版 CLAUDE.md（20-30 行）
- 提 PR，全員 review
- **不建議一次性把團隊所有規矩都塞進去**——先最硬的幾條

<a id="第-3-周建团队审核约定"></a>
### 第 3 周：建團隊稽核約定

- 討論哪些目錄 / 檔案 必須 L3 / L4 稽核
- 哪些絕不能讓 AI 動
- 寫進 CLAUDE.md 或單獨文件

<a id="第-4-周扩展--共享"></a>
### 第 4 周：擴充套件 + 共享

- 試點成員把已經好用的 Custom Commands / Skills 放到 `.claude/commands/` `.claude/skills/`（專案級）
- 其他成員拉取後，先核對所需依賴、許可權和個人憑據，再在練習任務中驗證
- 收集反饋、微調

<a id="30-天后的常态"></a>
### 30 天后的常態

- 按試點結果決定哪些場景繼續推廣
- 每月收集使用反饋，按季度或版本節點整理 CLAUDE.md
- 新 Skill / Command 走 PR
- 月度回顧："哪些用得好、哪些沒人用、CLAUDE.md 要不要砍"

<a id="本章小结"></a>
## 本章小結

- **共享 vs 私有**：專案規則和擴充套件經稽核後共享；個人設定、憑據與任務材料按實際內容區分
- **`.gitignore`** 先排除 `.claude/settings.local.json` 與本地憑據；`.mcp.json` 共享前檢查是否含金鑰
- **CLAUDE.md 走 PR**，每季度整理，硬性上限防膨脹
- **三個典型坑**：金鑰進 git / 標準不一致 / 擴充套件不共享——各有預防方法
- **Git 和 Claude 搭檔**：先檢查並儲存需要的版本；分支組織歷史，不能代替工作區恢復；提交和釋出分別確認
- **30 天接入路線**：第 1 周試點、第 2 周初版 CLAUDE.md、第 3 周稽核約定、第 4 周擴充套件共享

<a id="动手任务"></a>
## 動手任務

<a id="任务-1验证忽略规则与已跟踪文件10-分钟"></a>
### 任務 1：驗證忽略規則與已跟蹤檔案（10 分鐘）

先進入你有權維護的 Git 專案。本節在**普通終端**操作；沒有 Git 基礎時請先在練習倉庫完成。

1. 開啟專案根目錄的 `.gitignore`，按 25.1 加規則，保持註釋獨佔一行。
2. 執行 `git check-ignore --no-index -v -- .env .claude/settings.local.json`，確認目標路徑命中預期規則。
3. 執行 `git ls-files -- .env '.env.*' .claude/settings.local.json`，檢查這些路徑是否已經被跟蹤。若有輸出，先核對內容與團隊需要，不要直接刪除本地檔案。
4. 若某個個人檔案確實不應被跟蹤，先備份本地副本、確認忽略規則，再用 `git rm --cached -- "实际文件路径"` 將它移出跟蹤。引號中的文字必須換成剛確認的具體路徑；不要加 `-f` 強行繼續。這個動作還需要隨下一次提交生效，也可能影響同事下次更新時的檔案，團隊成員應提前保留自己的副本。
5. 檢視 `git diff --cached --stat` 和具體暫存差異，按專案流程處理這次變更。只移出跟蹤**不會刪除舊提交中的內容**；如果舊內容含已洩露金鑰，按 25.3 先撤銷或輪換。

**成功標誌**：你能區分“忽略規則匹配”“當前是否被跟蹤”“歷史是否曾儲存”三個問題，並知道本次檢查覆蓋了哪些路徑。

<a id="任务-2排查一组已知配置路径的历史10-分钟"></a>
### 任務 2：排查一組已知配置路徑的歷史（10 分鐘）

這只是縮小排查範圍的練習，不能代替完整的憑據掃描。在專案根目錄的普通終端執行：

```sh
git log --all --name-only --format=oneline -- .env '.env.*' .claude/ .mcp.json
```

如果開啟分頁器，按 q 退出。結果顯示這些路徑涉及的提交和檔名，**並沒有檢驗檔案內容是否含金鑰**。先定位可疑提交，再在本地或維護者協助下核對內容；不要把可能含憑據的完整差異貼到公開聊天裡。

發現仍有效且已暴露的金鑰，先撤銷或輪換，再處理歷史。如果沒有結果，只能說“這次選定路徑沒有查到”，不能據此斷言倉庫其他目錄、遠端或已刪除歷史沒有洩露。

**成功標誌**：記錄本次檢視的路徑、發現與未覆蓋範圍；有發現時，知道該交給哪位維護者繼續處理。

<a id="任务-3写一份团队-30-天接入计划15-分钟如你要给团队引入"></a>
### 任務 3：寫一份團隊 30 天接入計劃（15 分鐘，如你要給團隊引入）

<a id="如果你卡住了"></a>
## 如果你卡住了

**症狀 A：同事不願意用，覺得 AI 靠不住**
- 原因：合理——AI 有出錯案例、別人可能聽說過。
- 解決：**低風險任務起步**——讓他們先用在"寫週報草稿"這種最安全的任務，建立信任後再擴大。**不要強推**。

**症狀 B：團隊 CLAUDE.md 改動總是引起爭吵**
- 原因：規則背後的價值觀分歧。
- 解決：爭議大的條目**先不進**——放到專門文件（`docs/style.md`）討論，達成共識再移回 CLAUDE.md。

**症狀 C：金鑰已經 push 了怎麼辦**
- 原因：手滑或 `.gitignore` 晚了。
- 解決：先撤銷或輪換洩露憑據，再聯絡維護者檢查訪問記錄與處理歷史。不要把刪除檔案、清空分支或新建倉庫當成清除了所有副本；具體步驟見 25.3 的官方說明。

<a id="-支线-25aclaude-code-和-cicd-的边界"></a>
## 🌿 支線 25.A：Claude Code 和 CI/CD 的邊界

> **這段講什麼**：有人問"能不能把 Claude 接到 GitHub Action 裡自動審 PR"——能，但有邊界。
> **什麼時候回頭讀**：你的團隊想把 AI 深度整合進自動化流水線時。

<a id="能做什么"></a>
### 能做什麼

- **PR 自動稽核**：每次開 PR 觸發一次 Claude 審查，結果評論到 PR
- **自動生成 CHANGELOG**：每次打 tag 讓 Claude 生成發版說明
- **自動回覆 issue**：常見問題 Claude 先答，人工 review

**具體怎麼做**：先檢視 [Claude Code 的 GitHub Actions 整合](https://code.claude.com/docs/en/github-actions)及其授權配置，也可以學習非互動模式（`claude -p "..."`）。這些任務會使用模型服務，呼叫許可權和預算需要單獨配置。

<a id="本书建议的起步边界"></a>
### 本書建議的起步邊界

零基礎團隊先把自動化範圍放在生成草稿、總結差異和輔助檢查上。合併 PR、部署與生產配置修改，按團隊現有的稽核、測試和釋出許可權執行；不要因為接入 Claude 就繞過這些控制。

合併提交通常可以透過後續提交撤銷部分程式碼變化，但釋出、資料遷移或外部呼叫的影響未必一同逆轉。因此，“可以 Git 回退”不代表整項操作沒有代價。這裡是本書對入門流程的建議，不是聲稱 Claude Code 無法參與更成熟的自動化系統。

<a id="一个踏实的入口"></a>
### 一個踏實的入口

從**低風險 + 易觀察**的開始：

- Claude 自動給 PR 打 summary 評論（只說看到了什麼，不給評判）
- 觀察幾周，調整 prompt
- 質量穩定後再加審查評判
- 每次擴大自動化範圍，都補上對應驗證、授權與失敗處理

<a id="和本书定位的关系"></a>
### 和本書定位的關係

本書是**零基礎入門**——CI/CD 整合是**進階話題**。先把互動式的 Claude Code 用熟、團隊協作建好，再考慮 CI。
