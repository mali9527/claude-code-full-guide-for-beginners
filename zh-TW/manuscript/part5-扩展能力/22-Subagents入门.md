<a id="221-独立的是工作记忆不是整台电脑"></a>
## 22.1 獨立的是工作記憶，不是整臺電腦

**Subagent（子智慧體）**是主 Claude 委派出去的專項助手。它在自己的上下文裡讀取材料，完成後把結果交回來。假設你只想知道“這份小程式有沒有漏掉空輸入”，子智慧體可以檢查相關檔案，再返回幾條有位置、有理由的問題；主對話不必持續擺著它看過的全部材料。

*圖：分開任務與上下文，仍需協調共享檔案的寫入。*
<!-- /diagram: FIG-025 -->

這個分工像請同事做一次專項審查，但不代表換了一個不會犯錯的人。子智慧體也會漏讀、誤解和過度推斷。你的驗收物件仍然是報告中的證據，而不是“它叫程式碼審查專家”這個頭銜。

**獨立上下文也不等於獨立資料夾。**預設情況下，子智慧體仍在專案環境裡工作；如果給了編輯能力，它可能修改你正在看的同一批檔案。需要檔案副本隔離，是另一個配置問題。對於本章第一次練習，我們只提供讀和搜尋工具，讓任務範圍保持清楚。[子智慧體官方文件](https://code.claude.com/docs/en/sub-agents)

技能與子智慧體可以配合：技能提供步驟，子智慧體提供獨立執行位置。有的技能也能配置成在子智慧體裡執行。因此你真正要決定的是“這件事是否需要獨立閱讀大量材料”，而不是看到任務複雜就堆更多角色。

<a id="222-创建一个真正收窄工具范围的审查员"></a>
## 22.2 建立一個真正收窄工具範圍的審查員

本章把檔案放在專案的 `.claude/agents/book-code-reviewer.md`。它與技能的路徑不同：這裡是 `agents` 目錄下的一份 Markdown 檔案，不是每個角色一個 `SKILL.md`。`book-` 字首只是為了降低名稱衝突。

**Mac：**

```bash
mkdir -p .claude/agents
touch .claude/agents/book-code-reviewer.md
open -e .claude/agents/book-code-reviewer.md
```

**Windows PowerShell：**

```powershell
New-Item -ItemType Directory -Force .claude\agents
New-Item -ItemType File .claude\agents\book-code-reviewer.md
notepad .claude\agents\book-code-reviewer.md
```

檔案已存在就直接開啟，別覆蓋自己的舊版本。填入下面的角色文字；`tools` 表示給這個角色哪些工具，`Read` 讀檔案，`Grep` 搜內容，`Glob` 按名字找檔案。

```markdown
---
name: book-code-reviewer
description: 只读检查指定代码中的明确错误，给出位置、触发条件和修复建议
tools: Read, Grep, Glob
---
只检查委派消息指定的文件及理解它所必需的关联材料，不修改文件。
重点检查空输入、边界值和错误处理；只报告能说明触发条件的问题。
每条发现写明文件位置、原因、建议；推测必须标为待验证。
报告最后说明检查范围、未执行哪些测试。没有问题时如实说明，不能凑数。
```

本例沒有授予 `Bash`、`PowerShell`、編輯工具或外部工具。**去掉 Write / Edit、卻保留任意 shell 命令，並不能保證只讀**，因為命令同樣能寫檔案。這裡的工具收窄是為了本次練習；它也意味著審查員不能執行測試，報告必須承認這個限制。

儲存後，如果這是第一次建立 `agents` 目錄，重新啟動會話再委派。舊教程常讓你用 `/agents` 開啟建立嚮導；當前版本已移除這個終端嚮導，可以讓 Claude 幫寫檔案，也可以像這裡一樣手工建立。

<a id="223-给它一件能验收的任务"></a>
## 22.3 給它一件能驗收的任務

挑一份你能看懂的小檔案開始。如果沒有程式碼，可以讓主 Claude 在練習專案裡新建一個十幾行的示例，例如“根據人數平分費用”，再由你檢查內容。不要第一次就讓審查員“檢查整個電腦有沒有問題”，那既沒有邊界，也無法判斷它是否完成。

假設練習檔案叫 `split-bill.py`，在 Claude Code 裡提出：

```text
请委派 book-code-reviewer 检查 @split-bill.py。重点看人数是 0、负数或缺失时怎样处理。不要修复；把发现、证据位置和未验证的部分一起交回。
```

觀察會話中是否出現該角色的委派記錄，而不只是主 Claude 說“我來扮演審查員”。兩種結果可能同樣有用，但只有前者驗證了你剛建立的角色確實被使用。然後開啟報告提到的行，看看問題是否真實存在：如果檔案已經檢查人數，報告仍說沒有檢查，就不能因為它寫了行號而直接接受。

這裡“沒跑測試”是清楚的邊界，不是必須藏起來的缺陷。你可以讓主 Claude 在另一步執行對應測試；也可以先請它給出復現輸入，再由你手動試。**靜態閱讀發現問題、實際執行驗證問題、最終決定怎樣修改，是三個不同動作。**把它們分開記錄，你才知道結論有多可靠。

<a id="224-什么时候值得委派怎样写好派工说明"></a>
## 22.4 什麼時候值得委派，怎樣寫好派工說明

適合委派的是結果明確、材料較多的專項工作。例如從十份文件裡找出某個術語的不同用法，或檢查一段程式碼與說明檔案是否矛盾。主對話告訴它要查什麼，它返回有限條證據，主對話就能繼續原來的任務。

不適合為之新建角色的，是一句話就能回答的解釋、需要你不斷挑選措辭的編輯，或者根本還沒說清楚的問題。這些任務通常先留在主對話更順暢。不是子智慧體絕對不能多輪繼續，而是每次轉交、補充背景和彙總，都有額外成本。

給委派訊息寫上四件事：物件是什麼，重點問題是什麼，允許做哪些動作，回來交什麼。比如“只看兩份檔案，列出名稱不一致處，不修改，最多五條並給位置”，比“深入徹底稽核一切”更容易完成。材料如果依賴你剛才的一段討論，也要帶上必要背景；別假定角色一定知道主對話裡所有隱含約定。

最後，不要把“派出去”當成“我不用再看”。主 Claude 彙總報告時也可能遺漏限制，你應保留最初報告裡“未執行測試”“未檢視某目錄”等內容。真正省下的是重複翻閱材料的負擔，而不是對結果作判斷的責任。

<a id="本章小结"></a>
## 本章小結

- 子智慧體用獨立上下文做專項工作，再把結果交回。
- 專案角色檔案放在 `.claude/agents/`。
- 本章審查員只給 `Read, Grep, Glob`，不會執行測試。
- 有 shell 工具就可能透過命令寫檔案，不能僅憑沒有 Edit 宣稱只讀。
- 獨立記憶不等於獨立檔案副本，報告也不等於驗證透過。

<a id="动手任务"></a>
## 動手任務

**任務 1，約 15 分鐘：**建立審查員，對一個小檔案提出明確問題。成功標誌是看到委派記錄，報告包含可核對的位置，並說明未執行測試。

**任務 2，約 10 分鐘：**挑報告中的一條發現，回到檔案和實際輸入中核實。成功標誌是你能說出它是確認問題、誤報還是仍需驗證，而不是隻儲存了報告。

<a id="如果你卡住了"></a>
## 如果你卡住了

**找不到角色：**檢查 `.claude/agents/` 路徑、副檔名和 `name`；第一次建立目錄後重開會話。不要繼續尋找已移除的舊嚮導。

**主 Claude 自己回答了：**明確要求委派給 `book-code-reviewer`，並檢視實際呼叫記錄。如果環境限制不支援，記錄限制，不把模擬角色當成成功委派。

**它要求執行測試但沒工具：**這符合本章許可權設計。把測試交給主對話處理，或說明本次只做閱讀檢查，不為消除提示隨手加上全部工具。

<a id="-支线-22a并行审查怎样避免彼此覆盖"></a>
## 🌿 支線 22.A：並行審查怎樣避免彼此覆蓋

這段講多個助手同時工作；當一個任務確實能拆成獨立問題時回來讀。

可以讓一個角色查程式碼邏輯，另一個查文件描述，但兩者最好返回報告，由一個明確的負責人統一修訂。若兩個有寫許可權的助手同時修改同一檔案，獨立上下文並不會替你解決覆蓋和衝突。先約定誰改哪一部分，往往比增加助手數量更有效。

需要獨立程式碼副本時，可進一步瞭解 Git worktree，也就是同一倉庫的另一份工作目錄。當前子智慧體支援相關隔離配置，但這超出了本章練習範圍。即使用了不同目錄，遠端服務、資料庫或釋出目標也可能仍是同一個，不能把目錄隔離理解為所有副作用都被隔開。並行還會增加模型呼叫與彙總工作；實際速度取決於任務依賴和環境，不能簡單承諾“三個人一定快三倍”。

<a id="-支线-22b继续子任务与选择模型"></a>
## 🌿 支線 22.B：繼續子任務與選擇模型

這段講後續調整；等你已經有穩定的委派習慣，再考慮它。

子智慧體完成後，主 Claude 可以在支援的流程中繼續它的工作，補充一個更具體的問題。因此舊版“一次返回之後永遠不能繼續”的理解過於死板。無論是否繼續，都應給清楚的新增要求；不要讓第二次訊息推翻第一次邊界，卻沒有交代清楚。

本章沒有固定某個模型名稱，這讓角色繼承環境中適用的選擇。需要比較模型時，先固定檔案、問題和驗收標準，再看漏報、誤報、耗時與費用；不能只因模型名字更新，就斷言審查已經可靠。Fable、Opus 等模型的適用情況請回看第 15 章和附錄 J。模型升級不改變一個事實：返回報告必須有證據，工具許可權也仍需單獨檢查。
