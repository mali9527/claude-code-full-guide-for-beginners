## 20.1 技能負責一類任務，專案規則負責共同約定

**Skill（技能）是一份可重複使用的任務手冊**。例如，把會議記錄整理成紀要時，你希望分清“已決定”“還在討論”和“待辦”；沒說截止日期，就寫“待確認”。這些要求每次都一樣，值得儲存下來。

*圖：先看技能簡介，相關時再讀取完整說明。*
<!-- /diagram: FIG-023 -->

第 14 章的 `CLAUDE.md` 用來說明專案共同約定，例如“文稿用中文”“引用資料註明出處”。技能則回答“這類任務具體怎麼做”。兩者可以同時存在。一個專案每天寫週報，也可以把週報流程做成技能；判斷依據是內容的用途，而不只是使用頻率。

技能預設既可以由你輸入 `/技能名` 主動呼叫，也可以由 Claude 根據任務選擇。可供選擇的描述會佔用一部分上下文，正文在呼叫後才加入；已經加入的內容會隨對話保留，**不會在任務結束時立即自動消失**。所以按需載入能減少無關內容，卻不等於技能完全不佔空間。[技能官方說明](https://code.claude.com/docs/en/skills)

本章先把一個小流程做好。不要從幾十個技能包開始：你需要能解釋它讀什麼、產出什麼、怎樣判錯，之後才談更多功能。

<a id="202-建一个会议纪要技能"></a>
## 20.2 建一個會議紀要技能

本章使用**專案技能**：只在這個練習專案中使用，檔案放在專案根目錄的 `.claude/skills/meeting-notes/SKILL.md`。這裡的點號是資料夾名的一部分；`meeting-notes` 是我們給技能起的名字；`SKILL.md` 是入口檔案，注意不要儲存成 `SKILL.md.txt`。

先在第 3 章使用過的練習資料夾裡開啟終端。下面兩組選自己系統的一組，每行輸完按回車。

**Mac：**

```bash
mkdir -p .claude/skills/meeting-notes
touch .claude/skills/meeting-notes/SKILL.md
open -e .claude/skills/meeting-notes/SKILL.md
```

**Windows PowerShell：**

```powershell
New-Item -ItemType Directory -Force .claude\skills\meeting-notes
New-Item -ItemType File .claude\skills\meeting-notes\SKILL.md
notepad .claude\skills\meeting-notes\SKILL.md
```

`mkdir` / `New-Item -ItemType Directory` 負責建資料夾；接下來建立空檔案，再用文字編輯器開啟。如果 Windows 提示檔案已存在，就保留原檔案，直接執行最後一行，不要覆蓋已有內容。

在開啟的檔案中，第一行開始填寫以下**技能文字**。上下兩行 `---` 之間是說明標籤：`name` 表示名稱，`description` 說明何時使用；後面是給 Claude 的具體要求。

```markdown
---
name: meeting-notes
description: 将用户提供的会议记录整理成决定、讨论、行动项和待确认事项
---
只根据本次提供的会议原文整理，不搜索其它资料，不修改文件。
按“已决定 / 仍在讨论 / 行动项 / 待确认”四项输出。
行动项写明事项、负责人、截止时间；原文没有的信息写“待确认”。
提议没有被确认时，不得当作已作出的决定。
```

儲存後回到同一專案的 Claude Code。第一次新建 `.claude/skills` 這個頂層目錄時，退出後重新進入，便於確認它被發現。以後修改已有技能，當前版本通常會自動識別變化。另一個常見位置是個人目錄 `~/.claude/skills/`，其中 `~` 表示你的使用者主目錄；個人技能可用於這臺電腦上的多個專案。

<a id="203-用一段虚构记录验证它"></a>
## 20.3 用一段虛構記錄驗證它

在 Claude Code 輸入框中輸入 `/meeting-notes`，隨後空一格，附上下面這段虛構材料。斜槓命令輸入在 Claude Code 裡，不是在系統終端中執行。

```text
/meeting-notes 周一小组讨论：小陈提议下周五交初稿，小林说还要看资料是否齐全，大家没有定日期。已确认由小陈整理资料，小林检查引用。主持人说下次会议再定交稿时间。
```

我們不預設模型會逐字輸出什麼，而是檢查三個具體結果：整理資料和檢查引用進入行動項；“下週五”沒有被當成已確認截止日期；負責人未知、時間未知的地方沒有被補成聽起來合理的答案。

如果它把提議寫成決定，先指出原文哪句話證明尚未定案，讓它修正這次輸出；然後回到技能檔案，補一條更明確的判斷規則。再用一段新的虛構記錄重試。**只反覆測試同一段文字，容易把模板調成只會處理這個例子。**

確認技能有沒有被發現，先看 `/skills` 列表和輸入斜槓時的命令選單；確認這次有沒有呼叫，再看會話中的技能呼叫記錄。輸出剛好長得像模板，不能單獨證明技能已載入：Claude 也可能根據你這條訊息臨時寫出類似格式。

試用穩定以後，再用自然語言說“請把下面記錄整理成會議紀要”，觀察它是否選擇該技能。自動選擇不是每次都能猜中；你想確保使用某套流程時，直接敲技能名最清楚。

<a id="204-从一个好用的例子长成自己的工具箱"></a>
## 20.4 從一個好用的例子，長成自己的工具箱

寫第二個技能之前，先記下第一個技能的邊界：它整理文字，不錄音、不發郵件、不更新外部頁面。這樣你容易區分“輸出不滿意”和“我其實又增加了一種任務”。後者往往需要單獨流程，不能靠給舊技能再加幾十條限制來解決。

例如你準備做週報，可以先說明輸入是本週工作記錄，輸出包括完成結果、未完成事項和下週計劃。再寫三條檢查標準：未完成的事不能寫成完成；沒有數字就不編數字；需要他人配合的地方單獨列出。先讓 Claude 在對話裡執行一次，證明流程有效，再儲存為技能。

安裝別人分享的技能也遵循這個順序：開啟 `SKILL.md` 看懂任務範圍，看看有沒有附帶指令碼和外部訪問要求，在練習專案裡試用，然後再決定是否放到個人目錄。不需要因為作者給它起了“超級助手”的名字，就開放全部資料夾和賬戶。

技能內容變長時，把詳細模板、例子拆成同一目錄裡的普通 Markdown 檔案，在入口中寫明“做哪一步時讀哪個檔案”。這叫按需展開材料。拆分是為了讓流程更清楚，不能把關鍵限制藏到從未被讀取的附件裡。一次只改一個問題，並用一個正常輸入、一個資訊不全的輸入驗收，你的工具箱才會越用越穩定。

<a id="本章小结"></a>
## 本章小結

- 技能儲存特定任務的流程，`CLAUDE.md` 儲存共同約定。
- 專案入口是 `.claude/skills/<名字>/SKILL.md`。
- 技能可以主動呼叫，也可以由 Claude 選擇；下一章講手動入口。
- 技能正文按需載入，載入後仍屬於當前對話內容。
- 好不好用，要看事實有沒有被保留、缺失資訊有沒有被編造。

<a id="动手任务"></a>
## 動手任務

**任務 1，約 15 分鐘：**建立 `meeting-notes`，用上面的虛構記錄測試。成功標誌是未定日期仍為“待確認”，並能在選單中找到技能。

**任務 2，約 10 分鐘：**再寫一段含有反對意見的記錄。檢查它有沒有把爭議寫成共識；必要時修改一條技能要求，再試一次。成功標誌是你能說明這條修改解決了什麼問題。

<a id="如果你卡住了"></a>
## 如果你卡住了

**選單沒有技能：**核對專案目錄、`SKILL.md` 拼寫和隱藏的 `.txt` 字尾；如果頂層技能目錄剛建立，重啟會話。組織管理策略也可能限制自定義技能。

**自然語言沒觸發：**先直接執行 `/meeting-notes`。如果這樣能用，再把描述寫得更具體，不要把“偶爾沒選中”誤判成安裝失敗。

**輸出仍在編造：**縮小輸入，要求指出決定對應的原句。技能也是給模型的指令，不能保證每次正確；你仍要核對成果。

<a id="-支线-20a个人项目和账户同步技能"></a>
## 🌿 支線 20.A：個人、專案和賬戶同步技能

這段講技能從哪裡來；當同名技能有兩個版本，或你換裝置後找不到技能時回來讀。

個人目錄適合你自己反覆使用的流程，專案目錄適合跟著專案共享的流程。團隊成員拿到專案檔案，還需要在自己的環境裡確認可用。不要假設同名的個人技能與專案技能會自動合併；選單顯示的來源和實際呼叫記錄比猜測優先順序更可靠。為了少發生衝突，本書練習使用容易辨認的名字。

當前版本還可能顯示從 claude.ai 賬戶同步的技能。這和你手工寫在磁碟上的檔案是不同來源：要修改同步技能，應到該賬戶的技能設定裡更新，不能以為編輯下載快取就完成了同步。個人機器上的技能也不會因為登入同一賬戶，就自動成為所有云端任務能讀取的檔案。需要共享時，先明確對方實際執行在哪個環境，再決定交付專案檔案還是透過賬戶管理。詳見[技能來源與同步規則](https://code.claude.com/docs/en/skills#skills-synced-from-claudeai)。

<a id="-支线-20b技能权限与独立执行"></a>
## 🌿 支線 20.B：技能許可權與獨立執行

這段講技能如何與其它擴充套件配合；等你真的需要自動跑命令或委派長任務時再讀。

第一份技能刻意只整理輸入文字，沒有提前授予工具許可權。這使你可以先驗證流程，再決定是否讓它讀更多檔案。別把 `allowed-tools` 理解成“只允許這些工具”：它涉及技能執行時的授權行為，並不等價於只讀沙盒。需要限制工具範圍，應核對許可權設定，或採用下一章之後介紹的受限子智慧體。

技能通常在當前對話裡工作，也支援透過 `context: fork` 轉交獨立的子智慧體執行。因此，“技能一定共享上下文、子智慧體一定獨立”不是適用於所有配置的絕對分類。更實用的提問是：這份流程在哪裡執行，能讀到哪些材料，會把什麼結果帶回來？本章先使用預設方式；第 22 章再解釋獨立上下文與檔案共享的區別。
