# 第 10 章：信任校準——什麼時候信，什麼時候核對

> **本章在全書的位置**：第二部分 · 第 10 章 / 預估閱讀+動手時長：**主線 25-30 分鐘 + 支線 10 分鐘**
>

>

<a id="101-先承认一个事实ai-确实会犯错"></a>
## 10.1 先承認一個事實：AI 確實會犯錯

很多教程避開這個話題，本書正面講清楚：

> 📌 **AI 生成的內容和改動需要核對；是否可靠取決於具體任務、模型、工具和驗證方式**。

不是故意打擊信心——而是你**必須建立正確預期**才能用好它。具體來說：

- **邏輯錯誤**：生成程式碼可能邏輯自洽卻不符合真實需求，必須用具體輸入驗證
- **安全漏洞**：涉及許可權、認證、加密時，錯誤後果嚴重，需要專門審查與測試
- **邊緣情況**：AI 容易漏處理"空輸入"、"超長資料"、"特殊字元"這類邊緣
- **理解偏差**：你說 A，它可能理解成 B，做出來是 C

> 💡 **但這不代表 AI 不能用**——只代表**你不能盲目信**。下一節講怎麼分情況校準信任。

<a id="102-验证频谱按改动风险选检查深度"></a>
## 10.2 驗證頻譜——按改動風險選檢查深度

不是所有改動都要同樣深度稽核。用下面這個"頻譜"決定：

<!-- diagram: FIG-012 -->
![影響越大，檢查越仔細](../../../assets/illustrations/FIG-012/revisions/r02/zh-CN.png)

*圖：核對強度隨任務影響提高，不能只看助手的自信程度。*
<!-- /diagram: FIG-012 -->

| 改動型別 | 典型例子 | 建議深度 | 時間預算 |
|---------|---------|---------|---------|
| **L1 純展示格式** | 普通文件空行、無語義影響的排版 | 掃一眼 | 10-30 秒 |
| **L2 文字類 / 工具函式** | 改文案、重新命名變數、小的幫手函式 | 讀一遍 + 跑一下看效果 | 1-2 分鐘 |
| **L3 業務邏輯** | 改功能、加判斷條件、調介面引數、合併資料 | 細讀 diff + 跑測試 + 想 3 個邊緣情況 | 5-15 分鐘 |
| **L4 安全 / 支付 / 許可權相關** | 認證、加密、支付、使用者許可權、敏感資料處理 | **最嚴** + 靜態檢查工具（如有）+ 讓第二個人 review | 15-30 分鐘 |

<a id="怎么对号入座"></a>
### 怎麼對號入座

面對一個 diff 或命令，先問自己兩個問題：

1. **改的是什麼型別**？參考上面的 L1-L4
2. **改壞了能不能快速恢復**？能（有經過驗證的備份、不影響別人）→ 可減少恢復成本，但不能因此省掉高風險稽核；不能（影響生產、發給了客戶、改了使用者資料）→ 升一檔

表中時間只是練習安排，不是驗收時限。配置、重新命名、程式碼縮排也可能影響行為；有備份並不會降低安全、隱私或外部影響本身的風險。

<a id="103-vibe-review中间策略"></a>
## 10.3 Vibe review——中間策略

很多新手兩極化：要麼逐字檢查，要麼完全不看。**你需要學會 vibe review**（憑"感覺"快速審）——**不是偷懶，是高效**。

<a id="vibe-review-的动作"></a>
### vibe review 的動作

30 秒到 1 分鐘的流程：

1. **瞄一眼 diff 有幾個檔案**——和你預期的範圍一致嗎？
2. **掃改動範圍**——動的地方是你讓它動的嗎？有沒有"額外驚喜"（它順手改了別的）？
3. **關鍵詞搜尋**——如果是程式碼：有沒有 `TODO`、`FIXME`、`any`、被註釋掉的片段；如果是文件：有沒有錯別字、重複段落
4. **跑一下看效果**——開啟檔案快速瀏覽；跑個測試看有沒有報錯

**感覺都對 → Yes**
**有任何"怪怪的"感覺 → 升級到細審或 No 讓它澄清**

<a id="vibe-review-能处理什么不能处理什么"></a>
### vibe review 能處理什麼、不能處理什麼

✅ **能處理**：範圍很小、容易恢復且不涉及敏感內容的改動；不能給它套一個通用覆蓋比例
❌ **不能處理**：涉及安全、支付、使用者資料的任務——**永遠 L4 深度稽核**

<a id="104-必须细审的几类场景警戒清单"></a>
## 10.4 必須細審的幾類場景（警戒清單）

看到下列情況時，**不能 vibe review**，必須細審：

<a id="警戒-1触及敏感资源"></a>
### 警戒 1：觸及敏感資源

- 密碼、API key、證書、使用者隱私資訊
- 支付介面、賬單、退款邏輯
- 許可權判斷（誰能看什麼、誰能改什麼）
- 資料庫寫入、刪除、更新

<a id="警戒-2不可逆的改动"></a>
### 警戒 2：不可逆的改動

- `rm` 刪檔案（尤其批次）
- `git push --force`、`git reset --hard`
- 覆蓋性命令（`mv A B` 當 B 已存在）
- 資料庫 `DROP`、`DELETE`

<a id="警戒-3影响他人的改动"></a>
### 警戒 3：影響他人的改動

- 提交程式碼到團隊共享倉庫
- 改生產環境配置
- 發郵件、發 Slack 訊息
- 對外發布內容

<a id="警戒-4你不完全懂的领域"></a>
### 警戒 4：你不完全懂的領域

- 讓 Claude 寫一段你不懂語言的程式碼（比如你是 Python 使用者，它給你生成 Bash 指令碼）
- 改你沒接觸過的工具配置（比如 nginx、docker）
- 涉及你不熟悉的協議、API

📌 **警戒清單裡的任何一條出現 → 強制升級到 L4**，哪怕任務看著簡單。

<a id="105-建立你自己的信任档案"></a>
## 10.5 建立你自己的"信任檔案"

信任不是一個固定值。對不同型別的任務、不同的程式碼庫，Claude 的靠譜度不同。**記下來**，形成你自己的信任檔案：

<a id="怎么记"></a>
### 怎麼記

用一個簡單的筆記檔案（或記在 CLAUDE.md 裡，第 14 章講）：

```markdown
# 我对 Claude 的信任档案

## 高度信任（可 vibe review）
- 改文档文案、整理笔记
- 文件重命名、整理分类
- 简单的 Python / JavaScript 小脚本
- 生成 Markdown 表格

## 中等信任（细审）
- 修 bug（它容易改多余的地方）
- 加新功能（它容易漏边缘情况）
- 数据清洗（易出错，需跑样例验证）

## 低度信任（严审 + 测试）
- 认证 / 加密相关代码
- 数据库 schema 变更
- 正则表达式（经常写错）
- 金额 / 时间 / 时区处理

## 不用 Claude 做的
- 删除重要文件（宁可手动）
- 修改生产配置（Claude 给建议，我自己动手）
- 写法律 / 合同 / 医疗 / 金融专业内容
```

<a id="这个档案怎么更新"></a>
### 這個檔案怎麼更新

- **每次 Claude 犯錯**，記下是哪類任務——下次降低信任
- **每次它表現很好**，也可以記下——以後類似任務可以省稽核時間
- **每 2-3 個月回頭看**，隨著 Claude 版本升級、你自己熟悉度提升，重新評估

<a id="本章小结"></a>
## 本章小結

- AI 會犯錯——**按實際任務驗證，不能盲目信**
- **驗證頻譜 L1-L4**：按改動風險選稽核深度（純格式掃 10 秒、業務邏輯細審 15 分鐘、安全相關更嚴）
- **Vibe review**：對低風險改動的初篩；不是完整測試，也沒有通用覆蓋比例
- **必須細審的四類警戒**：敏感資源 / 不可逆 / 影響他人 / 你不完全懂的領域
- **建你自己的信任檔案**——哪類任務可以放手、哪類必須嚴審

<a id="动手任务"></a>
## 動手任務

<a id="任务-1给过去做过的改动分级10-分钟"></a>
### 任務 1：給過去做過的改動分級（10 分鐘）

回顧你前幾章已經讓 Claude 做過的改動，用 L1-L4 給每一件事打分：

- 改 `笔记.txt` 加編號 → L?
- `@日程.md` 改 12 小時制 → L?
- Ch 6 任務裡讓它精簡文字 → L?

**成功標誌**：你能對照 10.2 節的頻譜表做出判斷。

<a id="任务-2实战一次先判断后审核15-分钟"></a>
### 任務 2：實戰一次"先判斷後稽核"（15 分鐘）

**步驟**：
1. 找一個你真實想做的任務（任何型別）
2. **動手前**先想：這是 L 幾？需要多深稽核？
3. 用 Claude Code 做
4. 按你之前判斷的檔次稽核
5. 做完後反思：檔次判斷對嗎？如果重來，還是這個檔嗎？

**成功標誌**：你開始**有意識地在"做"之前先"判斷稽核深度"**，而不是每次都一刀切。

<a id="任务-3起草你的信任档案10-分钟"></a>
### 任務 3：起草你的信任檔案（10 分鐘）

新建一個檔案 `~/Desktop/ccguide-练习/信任档案.md`。照著 10.5 節的模板，寫下你目前對 Claude 的信任分級——至少 3 項高度信任 + 3 項需要嚴審。

**成功標誌**：你有了一份個人化的信任檔案，以後做類似任務時能直接查。

<a id="如果你卡住了"></a>
## 如果你卡住了

**症狀 A：判斷不出改動是 L 幾**
- 原因：前期對各類任務風險沒經驗。
- 解決：**新手傾向升一檔**——L2 的東西當 L3 來審。踩幾次坑後判斷力會準。

**症狀 B：vibe review 失誤了，放走了錯誤**
- 原因：vibe 能力還沒建立。
- 解決：記下這次失誤的型別（比如"加條件語句類的 vibe 審漏了"），下次同類任務升級到細審 1-2 個月，直到 vibe 重新穩定。

**症狀 C：對所有東西都想升檔到最嚴，審不過來**
- 原因：過度謹慎。
- 解決：**量化風險**——改壞了影響是"我自己多花 5 分鐘修" vs "客戶損失 1 萬塊"？兩個稽核深度當然不同。

<a id="-支线-10aai-最容易出错的几个典型场景"></a>
## 🌿 支線 10.A：AI 最容易出錯的幾個典型場景

> **這段講什麼**：具體哪些情況下 AI 特別容易翻車，提前知道就能針對性防禦。
> **什麼時候回頭讀**：你踩過坑、好奇是不是有規律可循。

<a id="错误热点-1时间和时区"></a>
### 錯誤熱點 1：時間和時區

- "今天" / "明天" / "三天後"——AI 有時不知道"今天"是幾號
- 時區換算——UTC / 北京時間 / 紐約時間，經常算錯
- 閏年、月底日期——`2024-02-29`、`1 月 31 日加一个月`

**防禦**：給它一個明確的日期（"2026-04-19"），或讓它先說今天是幾號再算。

<a id="错误热点-2金额和计算"></a>
### 錯誤熱點 2：金額和計算

- 浮點數精度（`0.1 + 0.2 !== 0.3`）
- 貨幣單位混淆（分 vs 元）
- 百分比 vs 小數
- 匯率換算

**防禦**：給具體例子驗證（`100.55 应该得出 150.82`），讓它寫測試跑一下。

<a id="错误热点-3正则表达式"></a>
### 錯誤熱點 3：正規表示式

AI 寫正則**經常漏邊緣情況**。

**防禦**：讓它寫正則時**必須附帶測試用例**：能匹配的例子 + 不能匹配的例子，跑一下驗證。

<a id="错误热点-4权限--认证"></a>
### 錯誤熱點 4：許可權 / 認證

- 誰能訪問什麼資源
- Token 重新整理邏輯
- 多使用者隔離

**防禦**：這類**必須人類嚴審 + 專門的安全測試**，不要靠 vibe review。

<a id="错误热点-5并发和竞态"></a>
### 錯誤熱點 5：併發和競態

- 同時改一個檔案
- 非同步操作的順序
- 鎖機制

**防禦**：這是專業領域，普通使用者碰到就 `/plan` + 找懂的人 review。

<a id="错误热点-6长文档上下文遗忘"></a>
### 錯誤熱點 6：長文件上下文遺忘

- 改長文件時，AI 可能忘記前面討論過的約定
- 同一對話聊太久，前面的設定"漂移"

**防禦**：關鍵設定**定期重申**；對話長了用 `/compact`（第 12 章講）或 `/clear` 重啟。

<a id="-支线-10b团队里怎么统一审核标准"></a>
## 🌿 支線 10.B：團隊裡怎麼統一稽核標準

> **這段講什麼**：如果你要和同事一起用 Claude Code，怎麼避免每個人標準不一致。
> **什麼時候回頭讀**：你公司 / 團隊開始大規模用 Claude Code 時。

<a id="问题"></a>
### 問題

不同人的"什麼該細審"不一樣——馬力覺得一眼過的東西，李四可能會翻車。

<a id="解决方案-1写一份团队审核约定"></a>
### 解決方案 1：寫一份團隊稽核約定

放在專案 CLAUDE.md 或專門的文件裡，例：

```markdown
# 团队 Claude Code 审核约定

## 必须细审（至少 L3）
- 任何涉及 `src/auth/` 目录的改动
- 任何涉及支付（`src/payment/`）、用户数据（`src/user/`）的改动
- 数据库迁移（`migrations/`）
- 对外 API 接口变更

## 可 vibe review（L1-L2）
- 改 README / 文档
- 前端样式调整
- 测试文件（已有测试的增补）

## 绝对不用 Claude 做的
- 数据库 DELETE / TRUNCATE
- 生产环境部署脚本
- 删除任何含有用户数据的文件
```

<a id="解决方案-2强制-code-review"></a>
### 解決方案 2：強制 code review

Claude 生成的改動，在 git commit message 裡標記（比如加 `[AI]` 字首），團隊成員 review 時格外留意。

<a id="解决方案-3自动化检查"></a>
### 解決方案 3：自動化檢查

對高風險目錄加 git hook / CI 檢查——敏感目錄改動必須多人 review、必須跑完整測試。

（這些都屬於進階團隊協作，Ch 25 會再講一些基礎。）
