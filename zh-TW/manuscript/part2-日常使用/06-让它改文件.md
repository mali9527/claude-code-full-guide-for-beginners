<a id="61-什么是-diff修改对比图"></a>
## 6.1 什麼是 diff（修改對比圖）

**diff** = difference 的縮寫，意思是"**修改前後的對比**"。在 Manual 模式且沒有預先允許該編輯時，Claude 通常會給你看 diff 並請求確認；其他模式和已儲存規則可能允許直接修改。無論是否彈出提示，都應檢視最終差異。

<!-- diagram: FIG-008 -->
![一眼認出修改前後](../../../assets/illustrations/FIG-008/revisions/r03/zh-CN.png)

*圖：減號與加號區分舊內容和新內容，逐行核對*
<!-- /diagram: FIG-008 -->

<a id="一个简单-diff-长什么样"></a>
### 一個簡單 diff 長什麼樣

假設原檔案 `笔记.txt` 內容是：

```
买菜
写周报
给妈打电话
```

你讓 Claude "每行前加編號"。它生成的 diff 是：

```
Edit: 笔记.txt

-  买菜
-  写周报
-  给妈打电话
+  1. 买菜
+  2. 写周报
+  3. 给妈打电话
```

<a id="怎么读"></a>
### 怎麼讀

- **紅色 `-` 開頭**的行：這行被**刪除**或**替換**（舊內容）
- **綠色 `+` 開頭**的行：這行是**新增**或**替換後**（新內容）
- 沒 `-/+` 的行：沒變，不用看

> 💡 **一句話記法**：減號是舊的、加號是新的。**你看到的是"檔案即將變成的樣子"**——綠色留下、紅色消失。

<a id="复杂-diff-多一个上下文"></a>
### 複雜 diff 多一個上下文

檔案很大時，Claude 只會顯示改動附近的幾行（叫"上下文行"），省螢幕：

```
Edit: config.txt
   ...
   port: 8080
-  debug: false
+  debug: true
   timeout: 30
   ...
```

中間的 `port` 和 `timeout` 行沒動（沒 `-/+`），顯示是為了讓你看到改動**在檔案的什麼位置**。

<a id="62-三档审核习惯别每次都细读"></a>
## 6.2 三檔稽核習慣——別每次都細讀

不是所有 diff 都要逐字看。新手最常見的錯誤是兩極化：**要麼不看、要麼糾結到看不完**。正確做法是**分三檔**：

| 檔 | 什麼時候用 | 看什麼 | 時間 |
|---|----------|-------|-----|
| **粗看**（掃 10 秒） | 小改動、低風險檔案（筆記、草稿、自己寫的說明） | 只看改動範圍合不合理、有沒有"意外加/刪"的檔案 | 10 秒 |
| **細審**（讀 1-2 分鐘） | 中等改動、涉及關鍵內容（簡歷、合同、程式碼） | 逐行讀 `-/+`，確認每一處改動都是你要的 | 1-2 分鐘 |
| **跑測試**（5-15 分鐘） | 涉及正式資料、會被別人看到的內容、程式碼 | 接受後，**實際執行一遍**看效果；程式碼類的跑測試 | 5-15 分鐘 |

> 📌 **關鍵判斷**：看影響範圍，也看恢復成本。純練習草稿可以粗看；涉及金額、許可權、正式資料或對外內容，即使能恢復檔案，也要仔細核對。表中的時間只是練習參考，不能到點就算驗收透過。

<a id="三个典型例子"></a>
### 三個典型例子

- **改草稿筆記**：粗看 → Yes
- **改你明天發給客戶的郵件**：細審每一句
- **改生產環境的配置檔案**：細審 + 跑測試 + 留備份

> 本章許可權選單與練習採用 Manual 模式且沒有相關預先允許規則。以下是教學示意；提示是否出現、選項原文和作用範圍以當前介面為準。若已有允許規則，先在練習專案中核對，不要刪除不明用途的全域性規則。

<a id="63-遇到编辑确认时怎样回答"></a>
## 6.3 遇到編輯確認時，怎樣回答

需要確認的 diff 彈出後，你有三種處理意圖（方向鍵選、回車確認）：

```
Do you want to apply this change?
❯ Yes
  Yes, and allow similar changes for the rest of this session
  No, tell Claude what to do differently
```

<a id="①-yes接受"></a>
### ① Yes（接受）

**選了就改**。檔案立刻被寫成新版本。適合你稽核透過、沒異議。

<a id="②-允许后续一类操作先看实际授权范围"></a>
### ② 允許後續一類操作（先看實際授權範圍）

這類選項會擴大後續許可，可能對應本次會話或儲存的規則。先讀實際介面寫出的工具、範圍與持續時間，不把所有“允許後續操作”都理解成同一種授權。

⚠️ **新手謹慎用這個**——如果任務有幾十次類似改動（比如批次改所有檔案裡的一個詞），用這個省事；但如果你不確定"類似"會擴散到哪，選普通 Yes 更穩。

<a id="③-no拒绝--告诉它怎么改更好"></a>
### ③ No（拒絕 + 告訴它怎麼改更好）

選了後 Claude 不會改，而是**等你說清楚**哪裡不對。

常見用法：
- "這個改動範圍太大了，只改 A 部分"
- "這種語氣不對，太正式了，口語化一點"
- "保留原來的結構，只替換關鍵詞"

Claude 會根據你的反饋**重新生成 diff** 給你看。不滿意再 No，直到滿意。

> 💡 **反覆 No 並不'煩 Claude'**——它不會生氣、不會累。反而比你將就接受然後再改回來**更省時間**。

<a id="只想改其中一小处"></a>
### 只想改其中一小處

可以拒絕這次提議，說明要保留和要調整的部分；也可以先停止操作，在自己的編輯器中修改後讓 Claude 重新讀取。不同介面的按鍵含義會變，不把字母 `e` 當作通用的“手改 diff”入口。

<a id="64-不只是改让它建删重命名"></a>
## 6.4 不只是改——讓它建、刪、重新命名

Claude 能做的檔案操作遠不止改：

<a id="建新文件"></a>
### 建新檔案

```
在当前文件夹建一个 todo.md，里面写今天的三件事：买菜、写周报、打电话。
```

在需要確認時，先看新檔案路徑和內容再允許；已獲許可時可能直接建立，隨後要親自開啟核對。

<a id="删文件"></a>
### 刪檔案

```
删掉 ~/Downloads/ 里所有超过一年没动过的 .zip 文件。
```

⚠️ **刪檔案是最危險的操作**——一旦 Yes，恢復可能很麻煩（圖形介面的"廢紙簍"有時能救、終端刪的**可能直接永久消失**）。

**做法**：
- **刪之前讓它先列出要刪的清單**（"先給我看要刪的檔名列表，別刪")
- **確認清單沒問題再讓它刪**
- 涉及重要檔案前**先備份一份到其他資料夾**

<a id="重命名--移动"></a>
### 重新命名 / 移動

```
把这个文件夹里所有 "2024-" 开头的文件，改名把前缀去掉
```

改名可能透過命令或檔案工具執行，不一定顯示文字 diff。先核對新舊路徑與是否覆蓋現有檔案，再檢視實際結果。

<a id="65-改错了怎么挽回四种路"></a>
## 6.5 改錯了怎麼挽回——四種路

改下去發現不對，先確認改動來自哪裡，再選擇覆蓋它的恢復方式：

<a id="路-1ctrl--z如果文件还在编辑器里打开"></a>
### 路 1：Ctrl + Z（如果檔案還在編輯器裡開啟）

Windows 編輯器常用 Ctrl+Z，Mac 編輯器常用 Command+Z，具體以應用選單為準。編輯器的撤銷通常針對它自己記錄的編輯。Claude Code 從外部修改的內容不一定進入編輯器撤銷棧；先檢查檔案，不要以為按一下 Ctrl+Z 就一定恢復了外部改動。

<a id="路-2claude-code-的-rewind"></a>
### 路 2：Claude Code 的 /rewind

在 Claude Code 裡打：

```
/rewind
```

會開啟**檢查點**（checkpoints）選單。選擇位置後，再決定恢復對話、受跟蹤的檔案改動，或兩者；執行前看清選項。命令、資料庫及外部系統的副作用不在通用恢復保證內。

在輸入框為空時按兩次 Esc，也會開啟同一檢查點選單；不是立即撤銷最後一步。

> 💡 這是 Claude Code 一個超好用的救命功能。**第 9 章會專門講** `/rewind` 的細節。

<a id="路-3用-git如果你在用-git"></a>
### 路 3：用 git（如果你在用 git）

如果已有 Git 版本管理，先檢視修改，不急著整體回滾：

```sh
git status
git diff
```

Git 是儲存檔案版本的工具，commit 是已儲存的一次版本。新手先在圖形介面或熟悉的人協助下，比較要恢復的單個檔案，保留目前的修改副本，再選擇需要的歷史版本。不要把 `git reset --hard` 當成通用撤銷鍵；它可能丟棄並非本輪產生的未提交改動。

> 💡 還不會 Git 時，先複製一份練習檔案作備份。不要為了照教程敲命令，把包含金鑰的整個目錄一次性加入版本庫。

<a id="路-4从备份恢复"></a>
### 路 4：從備份恢復

先確認備份已啟用、覆蓋目標檔案，而且存在修改前的版本，再使用 Time Machine、檔案歷史記錄或相應服務的恢復入口。雲端同步不等於完整版本備份；iCloud Drive 的已刪除檔案恢復，也不能視為所有普通檔案都有任意舊版本。

<a id="本章小结"></a>
## 本章小結

- **diff** = 修改前後對比；通常以 `-` 表示刪除、`+` 表示新增；顏色隨主題變化
- **三檔稽核**：粗看（10 秒）/ 細審（1-2 分鐘）/ 跑測試（5-15 分鐘）——**按恢復難度選檔**
- **三種處理意圖**：Yes（接受）/ Yes 類似改動都透過（謹慎用）/ No 告訴它哪裡不對
- **刪檔案最危險**——先列清單確認再真刪
- **改錯了四種挽回**：Ctrl+Z（編輯器裡）→ `/rewind` → git → 備份

<a id="动手任务"></a>
## 動手任務

練習先使用副本與 Manual 模式。確認框沒有出現時，核對是否已被規則允許並檢視實際結果；不必為尋找某個按鈕重複修改。

<a id="任务-1体验完整改文件流程8-分钟"></a>
### 任務 1：體驗完整改檔案流程（8 分鐘）

**步驟**：
1. 在 `ccguide-练习` 裡新建檔案 `日程.md`，寫 3 條安排（比如 "09:00 開會、11:00 寫稿、15:00 審閱"；時間明確才能轉換）
2. 啟動 Claude Code，輸入：`@日程.md 把时间从 24 小时制改成 12 小时制并加 AM/PM`
3. 稽核 diff，選 Yes
4. 切圖形介面開啟 `日程.md`，確認變化

**成功標誌**：檔案內容按要求改了，且圖形介面能看到。

<a id="任务-2主动用-no-纠正8-分钟"></a>
### 任務 2：主動用 No 糾正（8 分鐘）

**步驟**：
1. Claude Code 裡輸入：`@日程.md 大幅精简一下，只保留核心关键词，20 字以内`
2. 有確認提示時先拒絕並反饋；若已執行，則先檢查檔案，說明不滿意的具體部分，再提出修訂要求
3. 在反饋裡輸入："**保留原來的時間格式，但把描述換成更簡練的動詞開頭的短語**"
4. 檢視新差異；若出現確認則稽核後允許，沒有確認也要核對實際檔案

**成功標誌**：體驗到 No + 反饋是讓 Claude 調整的正常路徑。

<a id="任务-3用-rewind-回退5-分钟"></a>
### 任務 3：用 `/rewind` 回退（5 分鐘）

**步驟**：
1. Claude Code 裡輸入 `/rewind`
2. 看彈出的檢查點列表
3. 選任務 2 開始前的檢查點，再選恢復檔案或恢復檔案與對話；看清受跟蹤檔案清單再確認。沒有檔案恢復選項時，先查該點是否有可恢復的快照
4. 切圖形介面看 `日程.md` 是否回到任務 2 之前的狀態

**成功標誌**：檔案回到之前的樣子。

<a id="如果你卡住了"></a>
## 如果你卡住了

**症狀 A：diff 很長看著眼花**
- 原因：改動範圍大。
- 解決：先看有沒有你**不想動的檔案**出現在 diff 裡（比如你讓改 A，它順便改了 B）；有就 No 讓它只改 A。改動內容本身按三檔原則辦。

**症狀 B：選 Yes 後檔案沒變**
- 可能原因：操作失敗、目標路徑看錯、編輯器尚未重新載入，或檔案被鎖定。
- 解決：先查工具結果與實際路徑，儲存其它程式中的工作，再按具體錯誤處理。

**症狀 C：想 /rewind 但說"沒有可回退的檢查點"**
- 原因：會話、所選檢查點或快照保留狀態不符合預期；建立檢查點與存在可恢復檔案改動是兩回事。
- 解決：先確認是否由受跟蹤的編輯工具修改，再核對備份或 Git 儲存版本；不保證編輯器能撤銷外部改動。

<a id="-支线-6a批量改多个文件"></a>
## 🌿 支線 6.A：批次改多個檔案

> **這段講什麼**：一條命令改幾個、幾十個檔案。
> **什麼時候回頭讀**：你碰到"所有這些檔案都要做類似改動"的場景。

<a id="让它同时改多文件"></a>
### 讓它同時改多檔案

```
@第一章.md @第二章.md @第三章.md 
把这三章开头的"2024 年"都改成"2026 年"
```

Claude 會**依次對每個檔案生成 diff**，你一個個稽核。

<a id="三个-diff-都类似简化审核"></a>
### 三個 diff 都類似，簡化稽核

如果你已經看完第一個 diff 覺得很好、其餘兩個類似，選：

```
Yes, and allow similar changes for the rest of this session
```

就不會每個都彈。**但前提**：你真看清了模式，確信"類似改動都是安全的"。

<a id="更复杂跑个脚本批量改"></a>
### 更復雜：跑個指令碼批次改

```
把 ~/Documents/会议/ 下所有 .md 文件的首行日期格式统一成 2026-04-19 这种
```

Claude 可能**不生成 50 個 diff**，而是跑一個指令碼遍歷改。這種情況下它會展示指令碼讓你審（變成 "許可權-跑命令" 提示，見第 7 章）。

<a id="-支线-6b让它改得更准的三个技巧"></a>
## 🌿 支線 6.B：讓它改得更準的三個技巧

> **這段講什麼**：提高 Claude 改對率的三個習慣。
> **什麼時候回頭讀**：你發現 Claude 經常改偏、需要反覆糾正。

<a id="技巧-1给一两个期望的例子"></a>
### 技巧 1：給一兩個"期望的例子"

```
@章节列表.md 把每行末尾的字数统计格式从"(1200字)"改成"· 1.2k 字"
例子：原来 "第一章：开头 (1200字)" 改成 "第一章：开头 · 1.2k 字"
```

一個具體例子勝過十句解釋。

<a id="技巧-2明确不要做什么"></a>
### 技巧 2：明確"不要做什麼"

```
帮我把这段英文翻译成中文。
⚠️ 不要改变段落结构，不要合并句子，不要意译——保持直译的节奏。
```

告訴 Claude**別做什麼**和告訴它做什麼一樣重要。

<a id="技巧-3要求它先说计划再动手"></a>
### 技巧 3：要求它"先說計劃再動手"

```
@大文件.md 我想把它拆成三个章节。
先告诉我你打算怎么拆（在哪里断开、各章标题是什么），我 OK 你再开始改。
```

這樣是在自然語言裡提出“先給方案”的要求，有助於溝通，但不等於切換許可權模式。需要正式進入計劃模式時，使用 `/plan` 並核對狀態；其操作邊界見第 9 章。
