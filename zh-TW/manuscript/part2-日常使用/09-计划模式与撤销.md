<a id="91-先认清规划回退备份"></a>
## 9.1 先認清：規劃、回退、備份

遇到改錯，不要急著再補十個命令。先判斷你現在需要的是哪一種幫助：

<!-- diagram: FIG-011 -->
![計劃、回退、備份各管一段](../../../assets/illustrations/FIG-011/revisions/r01/zh-CN.png)

*圖：先規劃，再執行；檢查點和獨立備份的恢復範圍不同。*
<!-- /diagram: FIG-011 -->

| 工具 | 什麼時候用 | 你還要決定什麼 |
|---|---|---|
| `/plan` | 範圍或做法還沒想清楚 | 批准哪一部分方案 |
| Esc Esc 或 `/rewind` | 想退回一次對話裡的某個節點 | 選哪個點，恢復檔案、對話還是兩者 |
| Git 或檔案備份 | 需要長期儲存與恢復檔案 | 哪些改動值得儲存，恢復到哪版 |

**Esc Esc 和 `/rewind` 是同一個選單的兩個入口**，不是一套“快速撤銷”和另一套“高階撤銷”。這件事要先記住：開啟選單之後，檔案還沒有自動恢復。

這些工具幫你多留一個選擇，但無法讓所有錯誤消失。例如，已經發出去的郵件、已經扣掉的費用，都不會因為恢復對話而退回。操作前想清楚範圍，仍然是最省事的一步。

<a id="92-plan-计划模式让-claude-只看不动"></a>
## 9.2 /plan 計劃模式——讓 Claude 只看不動


<a id="是什么"></a>
### 是什麼

`/plan` 讓 Claude 先研究和提出方案，再進入修改階段。它會讀檔案，可能跑探索命令，也可能儲存計劃；因此不能把它理解成“除了說話什麼都不做”。

在本書不啟用繞過許可權的練習路徑裡，原始檔編輯要等你批准計劃。你也可以明確寫：“先分析，不安裝軟體、不訪問外部服務、不修改這些資料。”如果啟用了繞過許可權，或允許 Auto 在計劃時審查命令，行為邊界會變化；複雜環境按[官方 Plan 說明](https://code.claude.com/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode)核對。

<a id="什么时候值得先-plan"></a>
### 什麼時候值得先 `/plan`

- **複雜任務**：涉及多檔案、多步驟、你沒有把握
- **陌生專案**：你自己都沒看過的程式碼/資料夾，先讓它探查
- **高風險改動**：改生產配置、動重要資料前
- **你拿不準方案**：不知道是方案 A 好還是方案 B 好，讓它兩個都分析

> 💡 **反面**：簡單明確的改動（"把這個檔案裡'foo'全換成'bar'"）**不用 `/plan`**，直接做就行。

<a id="怎么用"></a>
### 怎麼用

**方式 A：啟動時進入**

```
claude --permission-mode plan
```

會話從計劃模式開始；你隨後仍能切換。

**方式 B：會話中切換**

對話裡打：

```
/plan
```

切進計劃模式。


**方式 C：批准後執行**

計劃完成時，讀清批准選項。初學者可以選擇**手動稽核編輯**；也可按 Shift+Tab 切回 Manual，然後說清楚這次批准的範圍。

不要只寫一個含糊的“好”。如果只認可前兩步，就說：“按前兩步修改，第三步暫時不做。”同樣，批准整理本地草稿，不自動意味著批准向外釋出。

<a id="一个典型的-plan--execute-流程"></a>
### 一個典型的 plan → execute 流程

```
（计划模式下）
你：@src/ 帮我看这个项目整体架构，分析一下如果我想加一个"用户反馈"功能，要改哪些文件
Claude：（读文件、分析）我看到这个项目是 ... 要加"用户反馈"，建议改以下文件：
  - A.tsx（新增表单）
  - B.ts（API 接口）
  - C.md（文档更新）
  步骤：...

你：方案看起来可行。把 A 和 B 按这个方案先做，C 我自己来。

（核对当前为 Manual 模式）
按 Shift+Tab 切到 Manual

你：按刚才的方案开始改 A 和 B
Claude：（生成 diff，正常审核循环）
```

這種"**先規劃後執行**"的流程叫 **plan → execute**，本書後面多處推薦。


<a id="93-esc-esc先打开菜单别急着恢复"></a>
## 9.3 Esc Esc——先開啟選單，別急著恢復

Esc 是鍵盤上的 Escape 鍵。**輸入框為空時連按兩次 Esc**，會開啟回退選單；如果輸入框還有沒發出去的文字，兩次 Esc 會先清掉輸入，而不是恢復檔案。怕記混時，直接輸入 `/rewind`。

把它想成開啟一個“回到哪裡”的選擇器。先找到造成問題的那條請求，再決定要恢復什麼。剛按完快捷鍵就開啟檔案檢查，會覺得“怎麼沒變化”，因為你還沒有完成選擇。

教學示例：你讓 Claude 用檔案編輯工具把 `笔记.txt` 的標題改掉，隨後發現改錯了。開啟選單，選中**提出改標題請求前的節點**，再選恢復檔案。操作後開啟檔案，核對標題。這個練習只用複製出來的筆記，不拿唯一的原件嘗試。

<a id="94-rewind选对检查点和恢复范围"></a>
## 9.4 /rewind——選對檢查點和恢復範圍

在輸入框執行：

```
/rewind
```

選單中的節點對應啟動一輪工作的使用者請求，不是每個字元、每次工具呼叫都有一個節點。挑選後，常見動作如下：

| 動作 | 用途 |
|---|---|
| 恢復檔案和對話 | 改動與討論都退回所選節點 |
| 只恢復對話 | 保留當前檔案，重新討論方向 |
| 只恢復檔案 | 保留討論，恢復被跟蹤的檔案編輯 |
| 從這裡摘要 / 摘要此前內容 | 整理上下文；不恢復磁碟檔案 |
| 返回 | 暫時什麼都不改 |

沒有可跟蹤的檔案改動時，不一定顯示恢復檔案選項。**檢查點主要記錄 Claude 的檔案編輯工具；shell 命令修改、外部程式修改和多數子代理修改不在同一恢復保證內。** 恢復舊會話後仍可能使用其檢查點，但快照受保留期限影響。不要把它當長期備份。[檢查點邊界](https://code.claude.com/docs/en/checkpointing)

<a id="一个典型场景"></a>
### 一個典型場景

你先讓 Claude 修改 A、B、C，再讓它處理 D、E、F。後來發現第二組任務方向錯了，可以選擇第二組請求前的節點。

這時先問自己：第一組結果是否保留？第二組裡有沒有你想留下的內容？如果有，先另存一份或儲存 Git 版本，再恢復。選單選擇正確後，還要開啟實際檔案核對，不憑“恢復成功”幾個字就繼續往下做。

<a id="哪些事情不会跟着倒退"></a>
### 哪些事情不會跟著倒退

假如 Claude 跑命令發出了一封郵件，恢復到發信前的對話，只是讓會話回到那個節點，收件人的郵箱沒有變化。同理，刪除雲端檔案、修改資料庫、付費呼叫、安裝軟體，都需要各自的處理方式。

如果同一個檔案也被你或另一個會話修改過，恢復舊快照還可能碰到這些新內容。先把仍需保留的版本另存，再回退，不要假設檢查點會自動替你合併所有人的修改。

甚至在本地，`rm`、`mv` 或指令碼生成檔案，也不能預設由 `/rewind` 恢復。任務涉及這些操作時，先保留原件或使用適合的版本控制；如果已經發生錯誤，先停下來查明事實，再做恢復。

<a id="95-检查点和-git-的关系"></a>
## 9.5 檢查點和 Git 的關係

如果你已經在用 git（程式碼版本控制），可能會問：**“有 Git 了還需要檢查點嗎？”**

答案：**都要。它們是不同層級的保護**。

| 工具 | 作用範圍 | 粒度 |
|------|---------|-----|
| **Claude Code 檢查點** | 當前或恢復後的會話 | 按啟動一輪工作的請求；並非所有中途補充訊息都有節點 |
| **git** | 你整個專案的版本歷史 | 按"提交級"——你 commit 一次就是一個節點 |
| **編輯器 Ctrl+Z** | 單個檔案在單次編輯中的修改 | 字元級——最細 |
| **系統備份**（Time Machine / 檔案歷史） | 全盤 | 按天/小時的快照 |

**搭配建議**：

1. **開始任務前 `git commit` 一下** → 有個"乾淨基線"
2. **任務中用 `/plan` / Esc Esc / `/rewind`** → 在 Claude Code 會話內快速回退
3. **任務完成後 `git commit`** → 新的"乾淨基線"
4. **過幾天回頭看發現有問題** → `git revert` 或從備份恢復

多留幾層恢復途徑，能降低返工代價。仍要確認備份真的包含你關心的檔案，尤其是未被 Git 跟蹤的資料。

> 💡 **不懂 git 也沒關係**——Ch 25（團隊協作基礎）會從零講 git 基礎。**現在記住**：Claude Code 的檢查點便於恢復被跟蹤的會話改動，git 是"跨會話的長期版本管理"。

<a id="本章小结"></a>
## 本章小結

- **先規劃，再回退**：`/plan` 幫你討論方案；Esc Esc 和 `/rewind` 開啟同一選單
- **`/plan` 計劃模式**：先探查和提出方案，適合複雜 / 陌生 / 高風險任務；plan → execute 是推薦流程
- **Esc Esc**：輸入為空時開啟選單，之後還要選擇檢查點與動作
- **`/rewind`**：選擇恢復對話、被跟蹤的檔案，或兩者；命令和外部副作用不能靠它撤銷
- **和 Git 配合**：檢查點便於嘗試，Git 和備份儲存長期成果

## 動手任務

<a id="任务-1用-plan-模式规划一个任务10-分钟"></a>
### 任務 1：用 plan 模式規劃一個任務（10 分鐘）

**步驟**：
1. 進 `ccguide-练习`，`claude --permission-mode plan` 啟動
2. 輸入：`@笔记.txt 我想把这份笔记改造成 GTD（Getting Things Done）风格的任务管理——规划一下改造方案，不要改文件`
3. Claude 會給你一個方案（只說不做）
4. 看方案：批准手動稽核編輯，或用 Shift+Tab 切到 Manual
5. 說"OK，按方案開始"
6. 正常稽核 diff

**成功標誌**：你體驗了"先規劃再執行"的流程，並且計劃模式下確實沒動檔案。

<a id="任务-2体验-esc-esc5-分钟"></a>
### 任務 2：體驗 Esc Esc（5 分鐘）

**步驟**：
1. Manual 模式下，請 Claude 用檔案編輯工具修改 `笔记.txt`（比如"把標題改成大寫"）
2. 稽核 → Yes → 改完
3. 確認輸入框為空，再按兩次 Esc
4. 選改標題前的檢查點，選擇恢復檔案；有確認提示時核對後再確認
5. 切圖形介面開啟 `笔记.txt` 確認回到了改之前

**成功標誌**：Esc Esc 撤銷成功，檔案回到未改狀態。

<a id="任务-3用-rewind-选一个更早的检查点5-分钟"></a>
### 任務 3：用 /rewind 選一個更早的檢查點（5 分鐘）

**步驟**：
1. 在 Claude Code 裡做 3-4 次改動（不用複雜，就是讓它改幾次檔案）
2. 打 `/rewind`
3. 看檢查點列表，按你每次提出的請求辨認節點
4. 選一個比"最近一次"更早的檢查點（比如第 2 次改動之前的）
5. 選擇恢復檔案和對話，確認後開啟檔案核對

**成功標誌**：被跟蹤檔案和對話都回到了所選節點。

<a id="如果你卡住了"></a>
## 如果你卡住了

**症狀 A：`/plan` 模式下讓它改東西它拒絕了**
- 原因：這是計劃模式的預期行為，它就是"不給改"。
- 解決：先確認方案，再按 Shift+Tab 切到 Manual，或選擇計劃批准中的手動稽核編輯

**症狀 B：Esc Esc 按了沒反應**
- 原因：輸入框裡有文字時，它可能只清掉輸入；或者這次沒有可恢復的檔案編輯
- 解決：連續按快一點；或用 `/rewind` 從列表選

**症狀 C：`/rewind` 恢復後檔案還是錯的**
- 原因：那個檔案被你**在 Claude Code 外面**（圖形介面、其他程式）改過——`/rewind` 不管外面的修改
- 解決：手動恢復，或從 git / 備份拿

**症狀 D：`/rewind` 說沒有檢查點**
- 原因：剛開始對話沒幾步，還沒生成足夠多的檢查點
- 解決：先檢查是否開啟了正確會話，再用 Git 或檔案備份核對可恢復版本；不要反覆嘗試猜測節點

## 🌿 支線 9.A：把 plan → execute 當預設工作流

> **這段講什麼**：一個值得養成的習慣——幾乎所有不那麼簡單的任務都先 `/plan`。
> **什麼時候回頭讀**：你用了幾周、開始做更復雜任務時。

<a id="我推荐的默认升级"></a>
### 我推薦的"預設升級"

早期（前 1-2 周）：大多數任務直接做，踩坑後學習。

中期（2-4 周）：**稍複雜任務（3 步以上、涉及多檔案）預設先 `/plan`**：

```
（启动就进 plan 模式）
claude --permission-mode plan

然后：
@目标文件/文件夹 分析一下，告诉我要做 X 该怎么做

看 Claude 方案 → 不满意就让它调整方案 → 满意后：
批准手动审核编辑，或按 Shift+Tab 切到 Manual
开始做
```

<a id="好处"></a>
### 好處

- **避免"做一半發現方案錯了"的浪費**
- **你有機會中途糾偏**（用嘴改方案比用 diff 改實際檔案快 10 倍）
- **複雜任務的"整體感"更強**

<a id="代价"></a>
### 代價

- 多花 3-5 分鐘討論方案
- 簡單任務走這一圈顯冗餘

> 💡 **判斷標準**：任務預計需要 Claude 做 **3 步以上**（多次改檔案或跑命令），先 `/plan`。1-2 步的直接做。

<a id="-支线-9brewind-的边界它能和不能救什么"></a>
## 🌿 支線 9.B：`/rewind` 的邊界——它能和不能救什麼

> **這段講什麼**：`/rewind` 具體能恢復什麼、不能恢復什麼。
> **什麼時候回頭讀**：你試圖 `/rewind` 但發現沒救回來想搞清楚原因。

<a id="rewind-能救的"></a>
### `/rewind` 能救的

- ✅ Claude Code 本次會話中**發出的訊息**（回退到那個時刻）
- ✅ 本次會話中 **Claude 用 Edit/Write 工具改過的檔案**（恢復到檢查點的內容）
- ✅ 檔案編輯工具建立且被檢查點跟蹤的檔案；恢復後仍應核對實際檔案狀態

<a id="rewind-救不了的"></a>
### `/rewind` 救不了的

- ❌ 你**在圖形介面 / 其他終端** 改過的檔案
- ❌ Claude **透過 `bash` 命令**改過的東西（因為 bash 命令的結果 Claude Code 不知道該怎麼回退）——比如它跑了 `rm file.txt`，`/rewind` 不會把檔案變回來
- ❌ Claude 安裝的軟體 / 改的系統設定
- ❌ 已經**被 git commit / push** 的東西（那是 git 的事）
- ❌ 快照已超過保留期限，或對應檔案未被跟蹤；正常恢復舊會話並不等於檢查點必然丟失

<a id="边界清楚了怎么办"></a>
### 邊界清楚了怎麼辦

**高風險操作的保護策略**：

| 操作型別 | 保護方式 |
|---------|---------|
| Claude 改檔案（Edit/Write） | 檢查是否有對應快照，再用 `/rewind` 恢復 |
| Claude 跑 `rm`、`mv` 等命令 | **`/rewind` 救不了** → **操作前手動備份 / git commit** |
| 裝軟體、改系統設定 | 手動記錄可逆的步驟 |
| 遠端操作（git push、調 API） | **操作前就要特別小心**——發出去的不一定收得回 |

<a id="心法"></a>
### 心法

`/rewind` 是**便利工具**而非**終極保險**。重要場景的終極保險永遠是：

1. **預防**：`/plan` 模式先規劃
2. **備份**：git commit / 手動複製一份
3. **分步小心**：一步一步做、每步驗證——而不是一口氣 10 步然後指望回退
